## 一、项目定位

本项目以**自研硬件 + 云端大脑**的技术路线，打造一款面向**大学生、年轻学习者及居家办公人群**的智能交互台灯。

产品保留台灯的基础照明属性，同时让它具备**听懂、回应、用灯光/屏幕/动作表达状态**的能力。学习场景是产品要落地的目标场景，但技术底座是一套**与具体硬件解耦的 AI 交互能力**——这套能力先做出来，再由后续硬件逐步承载。

- 产品名称：智能交互台灯（暂定）
- **产品主线**：学习场景（学习计时 / 任务显示 / 状态反馈）
- **技术主线**：AI 交互底座（语音闭环 → 云端大脑 → 动作/显示联动）
- 核心人群：大学生 / 年轻学习者 / 居家办公人群

> **技术路线的本质（一句话）**：对标 Autonomous Lamp 的交互理念，但**不把电脑塞进灯里**——它用 8 核 ARM64 + 6GB Linux 主机实现"具身 AI"，本项目用 **ESP32-S3 做身体 + 云端大模型做大脑**，用极低成本拿到同类的交互体验。

> **硬件策略说明（v0.3 新增）**：本项目硬件分两步走——**第一步用 ESP32-S3 开发板 + 面包板把"能力"跑通（正在做），第二步整体迁到 RIG-Arm 硬件**（ESP32-S3 + 5 路总线舵机 + 1.09" 圆屏 + 麦克风/扬声器）。
> 之所以不一开始就上 RIG-Arm，是因为**能力验证的成本远低于硬件调试成本**：在 ¥150 的面包板上把语音链路、指令协议、状态机调通，再迁到 RIG-Arm，可以把"功能不通"和"硬件不通"两类问题分开定位，避免同时调试两件事。
> 详见 §5.3 硬件演进路线 与 §5.4 硬件抽象层。

> **与对标产品的本质差异**：Autonomous Lamp 卖的是"具身 AI 机器人"（$499 起，靠摄像头 + 大模型 + 开放生态取胜）；本项目卖的是"**会反馈学习状态的 AI 台灯**"，靠**交互底座的场景化落地 + 极低的硬件成本**立足。

## 二、项目核心思路

以普通台灯为基础，结合桌面机器人交互能力，让台灯不仅提供照明，还能通过**语音、屏幕和机械动作**实现人与设备的互动。

主要思路：

- **先做能力、再上硬件**：语音交互、指令协议、状态机这些软件能力，先在开发板 + 面包板上跑通，再迁入 RIG-Arm。
- **迁移而非重写**：迁入 RIG-Arm 时只换驱动层，业务逻辑整体带走（见 §5.4 硬件抽象层）。
- **增加特色功能**：学习计时、任务显示、学习状态反馈——作为技能叠加在交互底座上。

> 一句话主线：**把"学习状态"变成台灯看得见、摸得着的反馈**——用灯光、屏幕、机械动作联动，让专注、休息、完成三种状态都有对应的感官信号。

### 3.2 技术路线对比（架构层）

> 本节对比的是**技术架构**，而非产品卖点。数据来源：Autonomous Lamp 官方规格与开源仓库（Autonomous OS 运行在树莓派/香橙派标准 Linux 边缘单板之上，ARM64 8 核 / 6GB，12V 5A 供电）。

| 维度 | Autonomous Lamp | 本项目（ESP32-S3 方案） |
|------|-----------------|------------------------|
| 硬件平台 | 树莓派 / 香橙派（ARM64 8 核 / 6GB，Linux SBC） | ESP32-S3（双核 MCU + 8MB PSRAM） |
| 功耗与供电 | 12V 5A = **60W** | 5V 0.5–2A ≈ **2.5–10W**（差 6–24 倍） |
| 核心架构 | 身体/大脑解耦，**大脑在灯内**（本地跑 Autonomous OS） | 身体/大脑解耦，**大脑在灯外**（ESP32 只做身体） |
| "开灯"指令 | Lamp Server 本地意图，离线处理 | ESP-SR MultiNet 离线命令词（≤200 条固定命令） |
| 复杂语义指令 | 本地大模型可处理（如"看下天气""总结邮件"） | **必须上云**（设备端无 LLM 算力） |
| "大脑"落点 | 灯内 Linux 主机（可外接 Agentic Gateway） | **云端大模型 API**（局域网 Ollama 仅作开发期降级） |
| 模型可插拔 | **整个 agent 运行时**（Claude Code / Codex / OpenCode / Hermes 等） | **模型 API 后端**（统一为 OpenAI 兼容接口） |
| 离线可用性 | **完整闭环**（断网照常工作） | **降级可用**（仅固定命令词，复杂指令失效） |
| 摄像头视觉 | 广角 + 人脸追踪（核心卖点） | 无（不做） |
| 相对成本 | 高（SBC + 8 核 + 6GB + 5 舵机） | **低**（MCU + 云端 API） |

#### 三个不能混淆的差异（这三点决定方案成败）

**① "解耦"方向相反，不能简单类比**

两边都写"身体/大脑解耦"，但解耦的**方向是反的**：

| | Autonomous Lamp | 本项目 |
|---|---|---|
| 大脑位置 | 下沉到灯内（本地 Linux） | 上移到云端 |
| 意味着 | 断网断电都能用，隐私本地化 | 便宜、轻量，但**依赖网络** |
| 代价 | 硬件成本高（SBC + 6GB + 60W） | **拿"离线可用性"换"成本"** |

> 这笔交易必须被清楚地意识到：**"云端大脑"不是低成本的捷径，而是用离线能力换成本**。它直接决定了第一阶段退出标准 E1（不插电脑可用）能否达成——只有把服务端搬到云上才算真正解决，把服务端留在你自己电脑上只是把依赖换了个位置。

**② MultiNet 只能救"固定命令词"，不是自然语言的替代品**

| 能力 | MultiNet 可覆盖 | 必须上云 |
|---|---|---|
| 指令类型 | 开灯 / 关灯 / 亮一点 / 暗一点 / 开始学习 / 暂停 | 把灯调成适合写作业的暖光 / 我今天学了多久 / 帮我看下明天日程 |
| 约束 | ≤200 条（新版 300）、**不能含阿拉伯数字和特殊字符**、中文需转拼音标注 | 无限制 |

> 因此"离线可用"在本项目里是**降级模式**（保底能开关灯），不是"和云上体验等价"。做产品说明时不能宣称"断网也能正常用"。

**③ "可插拔"的粒度不同**

- Autonomous Lamp 换的是**整个 agent 运行时**（能在灯里跑 Claude Code 这类本地 agent，意味着它能执行复杂任务链）；
- 本项目换的是**模型 API 后端**（换 endpoint 与 key，模型在云端跑）。

> 不要把"能换模型"等同于"能换 agent"。前者是接入方式的灵活性，后者是运行时能力的差异——这也是 Autonomous Lamp 卖 $499 而我们做低价位产品的根本区别之一。

### 3.3 核心区别（产品层）

- Autonomous AI Lamp 强调**通用 AI 助手和桌面机器人体验**，其差异化壁垒在于**灯内计算主机 + 摄像头视觉 + 开放技能生态**——三者本项目均不投入（分别替换为"云端大脑 + 不做视觉 + 专注单场景"）。
- 本项目更注重**低成本硬件上的能力实现**，以及**学习场景下的交互创新**，用"机械动作 + 灯光 + 屏幕"三者联动来表达学习状态，走"场景做透"而非"通用平台"路线。

## 四、核心创新点

### 1. 机械动作交互

利用 RIG-Arm 的总线舵机实现灯头点头、左右转向，让机械动作与学习状态对应：

- 完成任务时**点头**（正向确认）；
- 进入休息时**转向用户**（唤起注意）；
- 不同学习状态对应**不同机械动作反馈**。

### 2. 学习状态可视化

利用 1.09" 圆形彩屏显示**番茄钟、当前任务、学习时长和完成状态**。

### 3. 灯光与学习联动

根据学习、休息和任务完成状态调整灯光：

- 开始学习**自动开启灯光**；
- 休息时**调整亮度**（降为暖光/低亮度）；
- 结束学习后**关闭灯光**。

### 4. 项目创新点表述（对外统一口径）

本项目采用「ESP32-S3 本体 + 云端大脑」的低成本架构，将**智能照明、语音交互、机械动作与学习管理**整合为一台桌面台灯。

在保留基础照明、语音交互和机械动作的基础上，创新性地将**学习计时、任务状态显示与机械动作反馈**相结合，使台灯能够根据不同学习状态提供相应的**灯光、屏幕和动作反馈**——这是白牌番茄灯给不了、大厂 AI 学习灯不屑于做的中间地带。

## 五、硬件开发方案

### 5.1 当前阶段实际硬件（第一阶段）

第一阶段**不使用 RIG-Arm**，而是用 ESP32-S3 开发板 + 面包板做最小可验证系统。这是有意为之：**先把能力在低成本硬件上跑通，再整体迁到 RIG-Arm**——这样出问题时能立刻分清是"功能没写对"还是"硬件没接对"，不必同时调试两件事。

| 部件 | 型号 / 规格 | 接入引脚 | 状态 |
|------|-------------|----------|------|
| 主控 | ESP32-S3-DEVKITC-1（N16R8，16MB Flash / 8MB PSRAM） | — | ✅ 已跑通 |
| 麦克风 | INMP441（I2S MEMS 麦） | BCLK=GPIO16、WS=GPIO18、SD=GPIO17 | ✅ 已跑通（32bit 槽） |
| 照明 | HW-479 RGB 模块（只用 G 通道） | GPIO5（冷白）、GPIO21（暖白，面包板未接） | ✅ 已跑通 |
| 按键 | HW-483 轻触按键 | GPIO4 | ✅ 已跑通 |
| 状态灯 | 板载 / 外接 LED | GPIO14 | ✅ 已跑通 |
| 舵机 | 无（代码就绪，硬件未接） | 预留 GPIO6 / GPIO7（50Hz PWM） | ⬜ 未接 |
| 屏幕 | 无（编译期关闭） | 预留 I2C | ⬜ 未接 |
| 红外 | 无（代码就绪，硬件未接） | 预留 GPIO9 / GPIO10 | ⬜ 未接 |

> **成本量级**：主控约 ¥50–80，麦克风约 ¥10，其余模块各约 ¥3–5。第一阶段物料总成本控制在 **¥150 以内**。
>
> **已知硬件约束（实测踩坑，务必带入后续选型）**：
> 1. **ESP32-S3 只有 8 个 LEDC 通道（0–7）**，通道号 ≥8 会静默失效（`ledcSetup` 返回 0，`ledcWrite` 无效）。曾导致灯、舵机、蜂鸣器全部不工作。
> 2. **INMP441 必须用 32 bit 槽宽**（WS 周期 64 BCLK）。用 16 bit 槽会导致采样全 0 或低频漂移。
> 3. 面包板上暖白通道（GPIO21）未接线，调色温需设为 6500K 才能看到冷白通道满亮。

### 5.2 第二阶段硬件：整体迁入 RIG-Arm

第一阶段结束后，硬件**整体换成 RIG-Arm 电子套件**。这是本项目既定的硬件主线，不是备选方案。

| 能力 | 第一阶段（开发板） | 迁入 RIG-Arm 后 | 迁移工作量 |
|------|-------------------|-----------------|-----------|
| 主控 | ESP32-S3-DEVKITC-1 | 套件板载 ESP32-S3 | **小**：重映射引脚即可 |
| 麦克风 | INMP441（外接 I2S） | 套件自带 MEMS 麦 | **中**：重配 I2S 引脚与槽宽/增益 |
| 照明 | HW-479 单通道 | **需外接 LED 灯板**（套件不含照明） | **中**：新增灯板与驱动 |
| 机械动作 | 无（PWM 舵机代码） | **5 路 UART 总线舵机** | **大**：协议不同，驱动层重写 |
| 显示 | 无 | 1.09" 圆形彩屏 240×240 | **中**：新增驱动与 UI 布局 |
| 扬声器 | 无 | 套件自带 2W 喇叭 | **中**：新增 I2S 输出 + TTS 链路 |
| 摄像头 | 无 | GC0308 | **不投入**：保留接口，暂不开发 |
| 结构 | 面包板 | 机械臂结构（需改造灯头） | **大**：结构件设计 |

**迁移时必须提前处理的四个风险**：

| # | 风险 | 说明 | 应对 |
|---|------|------|------|
| R1 | **舵机协议完全不同** | 第一阶段 `motion.cpp` 写的是 50Hz PWM 舵机；RIG-Arm 是 UART 总线舵机（带位置反馈）。**这段驱动层代码无法迁移，需重写** | 把动作设计（点头/转向的时机与幅度）保留在能力层，只重写驱动映射 |
| R2 | **5 自由度对台灯是冗余** | 机械臂形态为抓取设计，台灯只需要 2–3 个自由度（底座旋转、灯臂俯仰、灯头俯仰） | 只用需要的 3 路，其余锁定；避免为冗余自由度做动作开发 |
| R3 | **供电严重超载** | 5 路总线舵机 + LED 灯板峰值电流远超开发板 USB 供电（500mA） | **必须独立电源**（如 12V/3A 适配器 + DC-DC 降压），与主控共地 |
| R4 | **ARM 形态资料较少** | RIG-Arm 官方对 ARM 形态的文档与测试少于 Hover/Puppy 形态 | 第二阶段预留专门时间做**单舵机标定 + 限位测试**，不要直接写动作 |

> **R1 是这次迁移最大的坑**：如果第一阶段在 `motion` 驱动上投入过多，迁到 RIG-Arm 时会全部作废。这就是 §5.5 把驱动层归为"可丢弃资产"的原因。

### 5.3 硬件演进路线

硬件分三代，**每代以"某个能力通过验证"为升级条件，不按时间排**：

| 代际 | 硬件形态 | 承载的能力 | 升级触发条件 |
|------|----------|-----------|--------------|
| **Gen-1（当前）** | ESP32-S3 开发板 + 面包板 + INMP441 + HW-479 + 按键 | 语音闭环、基础照明、串口调试 | §7 第一阶段三项退出标准全部达成 |
| **Gen-2** | **RIG-Arm 电子套件**（ESP32-S3 + 5 路总线舵机 + 1.09" 圆屏 + 麦/喇叭） | 机械动作、屏幕显示、语音能力迁移 | 单舵机标定通过 + 动作可编程 + 屏幕点亮 |
| **Gen-3** | RIG-Arm + **LED 灯板** + 3D 打印灯头/灯体 | 照明与机械整合、整机形态 | 三通道联动成立 + 整机可对外演示 |

> **原则**：**每代硬件只增加"当前阶段要验证的能力"**，不做提前集成。避免"硬件堆完了但功能还没验证"的返工。
>
> **中间不设过渡硬件**：不额外买 2 自由度云台——动作能力直接在 RIG-Arm 上验证（Gen-2）。这样虽然第二阶段难度更高，但少一次硬件投入和一次驱动重写。

### 5.4 硬件抽象层（HAL）—— 应对硬件更换的核心设计

既然硬件会换，固件就不能把硬件细节散落在业务逻辑里。**固件分三层，换硬件只改最底下一层**：

```
┌─────────────────────────────────────────────────┐
│  应用层（可迁移资产，硬件换代时不动）              │
│  语音链路 / 工具调用 / 状态机 / 学习技能 / 事件日志 │
├─────────────────────────────────────────────────┤
│  能力层（稳定契约，硬件换代时不动）                │
│  light.*  motion.*  display.*  audio.*  sensor.*  │
├─────────────────────────────────────────────────┤
│  驱动层（可丢弃资产，换硬件时重写）                │
│  PWM / I2S / 舵机协议 / 屏幕驱动 / GPIO 映射       │
└─────────────────────────────────────────────────┘
```

**能力层的稳定契约（上层只认这些，不认引脚）**：

| 能力 | 接口（语义化） | 换硬件时是否变化 |
|------|----------------|------------------|
| 照明 | `light.set(pct, cct)` / `light.scene(Study\|Office\|Rest\|Night)` | ❌ 不变 |
| 动作 | `motion.gesture(nod\|turn_to_user\|idle_breathe)` / `motion.look(yaw, pitch)` | ❌ 不变 |
| 显示 | `display.status(text, progress)` / `display.face(emotion)` | ❌ 不变 |
| 音频 | `audio.say(text)` / `audio.beep(kind)` | ❌ 不变 |
| 传感 | `sensor.light_level()` / `sensor.motion()` | ❌ 不变 |

**驱动层是唯一允许改的地方**：
- 引脚定义集中在 `firmware/include/config.h`，通过板型宏切换整套引脚映射：`LAMP_BOARD_BREADBOARD`（当前）→ `LAMP_BOARD_RIGARM`（第二阶段）；
- 迁移到 RIG-Arm 时，**只新增一套 board profile + 重写驱动的协议实现，不改业务代码**；
- 动作语义（点头/转向）在能力层定义，具体"哪路舵机转多少度"由驱动层映射——从 PWM 舵机换成 UART 总线舵机，不需要重写动作编排逻辑。

> **这条设计的实际价值**：现在写的 `lighting` / `pdm_mic` / `voice_client` 里，`voice_client`、工具调用、状态机、事件日志可**原样迁移到 RIG-Arm**；而 PWM 通道分配、I2S 引脚与槽宽、舵机协议这些必须重写——把它们隔离在驱动层，迁移时改动边界清晰，不会牵一发动全身。

### 5.5 资产可迁移性评估（控制迁到 RIG-Arm 的成本）

既然第二阶段要整体换硬件，就必须明确**哪些投入会白费**，把资源压在可迁移的部分。

| 资产 | 类型 | 迁到 RIG-Arm 后 | 说明 |
|------|------|-----------------|------|
| 语音链路（VAD → 录音 → ASR → LLM → 指令） | ✅ **可迁移** | 直接复用 | 与硬件无关，只需换麦克风驱动 |
| 工具调用协议（5 个 tool 定义） | ✅ **可迁移** | 直接复用 | 契约稳定，是长期资产 |
| 状态机 / 学习技能逻辑 | ✅ **可迁移** | 直接复用 | 纯软件 |
| 事件日志 / 串口命令系统 | ✅ **可迁移** | 直接复用 | 调试基础设施 |
| 动作语义设计（点头/转向的时机与含义） | ✅ **可迁移** | 直接复用 | 设计资产，不依赖舵机型号 |
| 灯光调色算法（色温混合 + gamma） | ✅ **可迁移** | 直接复用 | 只换输出通道，算法不变 |
| LEDC 通道分配 / PWM 参数 | ⚠️ **需重算** | 重新标定 | RIG-Arm 引脚不同，且舵机改走总线 |
| I2S 麦克风配置 | ⚠️ **需重调** | 重新配参 | 换成套件自带麦，槽宽/增益需重测 |
| **PWM 舵机驱动（`motion.cpp` 现有实现）** | ❌ **废弃** | **必须重写** | RIG-Arm 是 UART 总线舵机，协议不同（见 §5.2 R1） |
| 红外编解码（`ir_engine` / `ir_store`） | ⚠️ **暂缓** | 保留不动 | 后备方向，硬件未接，不建议继续投入 |
| 面包板接线 / 临时结构 | ❌ **一次性** | 丢弃 | 无迁移价值 |

> **结论（资源分配原则）**：**在迁入 RIG-Arm 之前，把 80% 的精力放在应用层（语音、工具调用、状态机），驱动层只做到"够验证"即可**。
> 反面案例：`motion` 用 PWM 写了一套完整实现，但 RIG-Arm 是总线舵机，这部分**确定会作废**；`ir_engine` / `timer_task` 从未上过硬件，属同类风险。这三块应停止继续投入，等硬件到位再写。

## 六、最小可行产品（MVP）

MVP 不是"一次做完一个完整台灯"，而是**按阶段拆成三个递进的 MVP**，每个都能独立验证一件事。

### 6.1 MVP-1｜语音闭环（当前阶段，已基本达成）

**目标**：证明"说话 → 灯响应"这条链路在真机上成立且可连续使用。

| 功能模块 | MVP-1 实现 | 状态 |
|----------|-----------|------|
| 智能照明 | 开关灯、亮度调节、4 个场景预设 | ✅ 已跑通 |
| 语音交互 | 语音指令控制灯光（VAD 触发 → ASR → 大模型 → 指令） | ✅ 已跑通 |
| 状态查询 | 串口 `status` 查询运行状态 | ✅ 已跑通 |
| 串口调试 | `mic test` / `mic probe` / `log` 等诊断命令 | ✅ 已跑通 |
| 机械动作 | —— | ⬜ 不在 MVP-1 范围 |
| 屏幕显示 | —— | ⬜ 不在 MVP-1 范围 |

**MVP-1 的验收（三项，缺一不可）**：
1. **不插电脑可用** —— 拔掉 PC，设备仍能响应语音（当前不满足，依赖 PC 上的服务端）；
2. **连续 10 次说话 ≥8 次正确执行** —— 当前实测 5 次触发、3 次成功（60%），未达标；
3. **换 WiFi 无需重新烧固件** —— 当前 SSID/密码硬编码，不满足。

> 这三条不过，MVP-1 就不算完成。**它们是第二阶段的入口条件**。

### 6.2 后续 MVP 增量

| 版本 | 新增能力 | 依赖硬件 | 对应阶段 |
|------|----------|----------|----------|
| MVP-2 | 脱离电脑（上云）+ 标准 tool calling + 手机配网 | **无**（仍用 Gen-1 开发板，纯软件） | 第二阶段 |
| MVP-3 | 语音/照明迁移到 RIG-Arm + 舵机基础运动 + 屏幕点亮 | **Gen-2：RIG-Arm 电子套件** | 第三阶段 |
| MVP-4 | 动作库 + 屏幕 UI + 灯光/动作/屏幕三通道联动 | Gen-2：RIG-Arm（+屏幕） | 第四阶段 |
| MVP-5 | 学习场景技能（番茄钟 / 任务列表 / 状态机） | 无（软件叠加） | 第五阶段 |
| MVP-6 | 整机形态（LED 灯板 + 3D 打印灯头） | Gen-3：RIG-Arm + 灯板 + 结构 | 第六阶段 |

### 6.3 明确不开发

- **摄像头视觉与行为识别** —— 成本高、隐私敏感、与"低成本"定位冲突；
- **复杂 AI 对话系统** —— 直接复用云端通用大模型，不自研；
- **自动学习行为分析** —— 需长期数据，MVP 阶段无价值；
- **红外家电控制** —— 列为**后备方向**，见第九章，硬件不接、代码保留但不继续投入。

### 7.2 第一阶段｜语音交互闭环（当前，进行中）

| 项 | 内容 |

| **硬件** | Gen-1：ESP32-S3-DEVKITC-1 + 面包板 + INMP441 + HW-479 + 按键 |

**已完成（有实机日志佐证）**

| 能力 | 状态 | 说明 |
|------|------|------|
| 双色温 PWM 照明 | ✅ | 4 个场景预设（Study/Office/Rest/Night），亮度与色温可调 |

|---|----------|----------|------|

> **E1 的严格定义（避免验收歧义）**：这里的"不插电脑"指的是**不依赖你自己那台 PC**，**不等于"离线可用"**。

> 若把 E1 误解为"完全离线可用"，就会误判为"要做本地大模型"，那是 Autonomous Lamp 那条 $499 的路线，与本项目的低成本定位冲突。

> **结论**：第一阶段的主链路已跑通，但 **E1/E2/E3 三项横跨到第二阶段才能真正达成**——因为它们的解法都是软件架构改造。因此第一、第二阶段可以视为**连续的同一个大阶段**，分界线是"从能演示到能脱离 PC 连续用"。

**本阶段踩过的坑（务必带入 RIG-Arm，避免重犯）**

| 坑 | 现象 | 根因 | 教训 |
|----|------|------|------|
| LEDC 通道越界 | 按键有日志但灯不亮，舵机/蜂鸣器一起哑 | ESP32-S3 只有 8 个 LEDC 通道（0–7），用了 8–12 | 换 RIG-Arm 后先核对主控外设上限 |
| I2S 槽宽错误 | 麦克风采样全 0（非零 0%） | INMP441 需 32 bit 槽（WS 64 BCLK），代码走了 16 bit | 迁移时先跑 `mic probe` 再调逻辑 |
| IRrecv 空指针 | 开机即 `Guru Meditation` 死循环重启 | 未 `enableIRIn` 就 `disableIRIn`，timer 为 NULL | 红外模块未启用前不要调用其 API |

### 7.3 第二阶段｜脱离电脑（上云 + tool calling）

| 项 | 内容 |
|---|---|
| **时间** | 2026-11 ~ 2026-12 |
| **硬件** | **不换**（仍用 Gen-1 开发板） |
| **目标** | 消除"必须连 PC"这个产品级缺陷，把指令协议从脆弱正则换成标准工具调用 |
| **为什么在换硬件前做** | 纯软件，风险低；做完可直接迁移到 RIG-Arm（见 §5.5） |

**主要任务**

| # | 任务 | 具体内容 |

| T2 | **设备直连云网关** | 设备主动外连 wss（不再依赖局域网固定 IP），服务端部署到云函数/轻量服务器；模型走云端（如百炼 qwen） |

| T4 | **离线兜底（建议做）** | 用 **ESP-SR MultiNet** 做固定命令词识别（开灯/关灯/亮一点/暗一点/开始学习/暂停），断网时保底可用。**注意边界**：≤200 条、不能含阿拉伯数字与特殊字符、中文需转拼音标注（见 §3.2 差异②） |

**退出标准**

| # | 标准 | 判定方式 |
|---|------|----------|
| E1 | **拔掉 PC，设备仍能语音开灯** | 关掉 PC，对着麦克风说"开灯"，灯亮 |
| E2 | **换 WiFi 只需手机操作，不重新烧固件** | 换一个 WiFi，用配网页面改完即恢复 |
| E3 | **工具调用成功率 ≥95%** | 100 次指令测试，错误 ≤5 次 |
| E4 | **端到端延迟 <3s** | ASR + LLM + 执行全流程计时 |

**风险**

| 风险 | 影响 | 应对 |
|------|------|------|
| 云端 ASR/LLM 有延迟与费用 | 体验差、长期成本不可控 | 做本地命令词兜底；对高频指令走本地分支 |
| 网络不稳定 | 断网即失效 | 断线重连 + 本地兜底 + 状态提示（灯效告知离线） |

### 7.4 第三阶段｜迁入 RIG-Arm（第一次换硬件，基础打通）

| 项 | 内容 |
|---|---|
| **时间** | 2026-12 ~ 2027-01（**预留 buffer，这是全项目硬件风险最高的一段**） |
| **硬件** | **Gen-2：RIG-Arm 电子套件**（ESP32-S3 + 5 路总线舵机 + 1.09" 圆屏 + 麦克风/喇叭） |
| **目标** | 把第一阶段验证过的能力整体迁移到 RIG-Arm，并打通舵机与屏幕的基础控制 |
| **不做的事** | 不写复杂动作编排、不做屏幕 UI 设计、不做整机结构——这些留给第四阶段 |

**主要任务（严格按顺序）**

| # | 任务 | 关键要点 |
|---|------|----------|
| T1 | **供电改造** | 5 路总线舵机峰值电流远超 USB 500mA，**必须独立电源 + 与主控共地**。这一步不做，后面所有调试都会被随机重启干扰 |
| T2 | **逐路舵机标定** | 一次只接一路：确认 ID、零位、行程限位、方向、速度。**先做限位保护再写动作**，避免撞机烧舵机 |
| T3 | **确定使用几路** | 建议只用 3 路（底座旋转 / 灯臂俯仰 / 灯头俯仰），其余锁定。台灯不需要 5 自由度 |
| T4 | **语音链路迁移** | 重配 I2S（套件自带 MEMS 麦），先 `mic probe` 验证采样正常，再跑闭环 |
| T5 | **屏幕点亮** | 1.09" 圆屏 240×240，先显示静态文本，确认驱动与刷新率 |
| T6 | **照明接入** | 外接 LED 灯板，复用第一阶段的调光算法，只换输出通道 |
| T7 | **能力层接口对齐** | 按 §5.4 把 `light/motion/display/audio` 四类接口在 RIG-Arm 上实现，业务层代码不改 |

**退出标准**

| # | 标准 |
|---|------|
| E1 | 3 路舵机可单独定位，且**限位保护生效**（超程不撞机） |
| E2 | 语音闭环在 RIG-Arm 上跑通（说话 → 灯响应） |
| E3 | 屏幕能显示文本与数值 |
| E4 | 整机连续运行 30 分钟不死机、不重启（验证供电足够） |

**风险（来自 §5.2）**

| # | 风险 | 应对 |
|---|------|------|
| R1 | 总线舵机协议与 PWM 不同，`motion.cpp` 必须重写 | 只保留动作语义设计，驱动重写 |
| R3 | 供电超载 | T1 优先做，独立电源 |
| R4 | RIG-Arm ARM 形态资料少 | 预留 buffer；先做单舵机最小测试再上整机 |

### 7.5 第四阶段｜动作、显示与三通道联动

| 项 | 内容 |
|---|---|
| **时间** | 2027-01 ~ 2027-02 |
| **硬件** | Gen-2：RIG-Arm |
| **目标** | 让"学习状态"通过**灯光 + 屏幕 + 动作**三条通道同时表达，这是本项目的核心差异化 |

**主要任务**

| # | 任务 | 具体内容 |
|---|------|----------|
| T1 | **动作库** | 语义动作：`nod`（点头确认）/ `turn_to_user`（转向用户）/ `idle_breathe`（待机呼吸）/ `shake`（否定）。每个动作含平滑加减速，避免抖动与异响 |
| T2 | **动作可用性测试** | 测噪声（dB@30cm）、动作时长、连续动作温升。**噪声超标就减少动作频次或降低速度** |
| T3 | **屏幕 UI** | 番茄钟（倒计时环）、当前任务、状态图标、简单表情 |
| T4 | **三通道联动协议** | 定义状态 → (灯, 屏, 动作) 的映射表，例如：专注 = 冷白 70% + 倒计时环 + 静止；休息 = 暖光 30% + 休息图标 + 转向用户；完成 = 灯光脉冲 + 对勾 + 点头 |
| T5 | **联动去重与节流** | 避免动作过频（如每次状态查询都点头），设置最小间隔 |

**退出标准**

| # | 标准 |
|---|------|
| E1 | 三种状态（专注/休息/完成）**盲测可辨**：遮住屏幕仅看灯光与动作，用户能说出当前状态 |
| E2 | 舵机噪声 ≤45 dB @30cm（不干扰学习） |
| E3 | 连续动作 1 小时无丢步、无明显温升 |

> **这是全项目最需要"做减法"的阶段**：动作不是越多越好。建议先只做 3 个动作（点头/转向/呼吸），验证用户是否接受，再考虑扩展。

| 约束 | 说明 |

## 八、市场与用户验证

### 目标用户

- 大学生；
- 年轻学习者；
- 居家办公人群。

### 重点验证问题 [市场校验]

| 编号 | 验证问题 | 证伪条件（建议） |
|------|----------|------------------|
| V1 | 用户是否愿意使用具有机械动作的智能台灯？ | 访谈中多数人认为"多余/吵"，或样机试用中主动关闭动作 |
| V2 | 学习计时和任务显示是否具有实际使用价值？ | 相对手机番茄钟/白牌番茄灯无增量价值 |
| V3 | 机械动作与灯光反馈是否能提升桌面交互体验？ | 2 周试用期内动作反馈被忽略或关闭 |
| V4 | "三者联动反馈"是否真的优于"便宜番茄灯 + 普通台灯"组合？ | 用户不愿为联动支付溢价 |

> **重要**：需要通过**实际访谈和样机测试**验证，而不是直接假设用户有需求。
> 尤其要警惕：番茄钟/计时是白牌十几元就能给的功能，用户可能反问"我为什么要为它付溢价"——这是本项目能否成立的第一道坎。

## 九、项目最终概述

本项目采用**两步走**的技术路径：先用 ESP32-S3 开发板 + 面包板把「语音交互能力」在最低成本硬件上跑通，再整体迁入 **RIG-Arm 硬件**（ESP32-S3 + 总线舵机 + 圆屏 + 麦克风/扬声器），最终通过结构整合形成一台具备**智能照明、语音交互、机械动作与学习管理**能力的桌面台灯。

产品不复刻 Autonomous Lamp 的"把电脑塞进灯里"路线，而是**用 ESP32-S3 做身体、用云端大模型做大脑**，在极低成本下获得同类的交互体验；差异化落在**「灯光 + 屏幕 + 动作」三通道联动**表达学习状态，而不是堆砌计时功能。

**项目核心不是重新发明一款 AI 台灯，而是用可控的成本把"会回应的台灯"做出来。**

### 现阶段最重要的三个目标

| # | 目标 | 对应阶段 | 判定 |
|---|------|----------|------|
| 1 | **把语音闭环做到"不用连电脑也能用"** | 第一、二阶段 | 拔掉 PC 说"开灯"能亮；连续 10 次 ≥8 次正确 |
| 2 | **干净地迁入 RIG-Arm，打通舵机与屏幕** | 第三阶段 | 3 路舵机带限位可动 + 屏幕点亮 + 语音迁移成功 |
| 3 | **用真实用户验证"三通道联动"是否值得做** | 第四、七阶段 | 三种状态盲测可辨；V1–V4 有明确结论 |

> **给当前阶段的提醒**：第一阶段的语音链路已经跑通，但它现在**离不开你桌上这台电脑**。在迁入 RIG-Arm 之前，务先把"上云 + 配网 + 工具调用"这三件纯软件的事做完——它们一旦完成，后面换硬件只是换驱动，不会再回到"功能要从头调"的状态。

### 红外家电控制 —— 后备方向说明

- **定位**：暂缓开发，作为**功能后备与可能的第二增长点**保留。
- **理由**：
  - 现有调研（`docs/02-市场调研与竞品分析.md`）显示"遥控器找不到/被藏/没电"是宿舍场景的高频真实痛点，红外学习模块硬件成本仅约 5 元，是低成本高确定性的入口；
  - 但其与"学习场景"主线叙事不同频，且会引入协议兼容（空调完整状态指令匹配）等额外技术复杂度。
- **触发条件（何时重启）**：当学习场景在用户验证中被证伪（V1–V4 任一关键假设不成立），或样机完成后有明确用户需求信号时，可将红外从后备提升为主线。
- **保留事项**：ESP32-S3 有足够 GPIO/外设，红外接收头（如 TSOP38238，约 2 元）与发射管在结构与主板布局上**预留接口位**，确保未来低成本启用，无需推翻重做。
- **代码现状**：`ir_engine` / `ir_store` 已写好但从未上过硬件，**本阶段停止继续投入**，等需要时再验证。
