## 零、触发原因：不是代码坏了，是阿里云账号欠费

### 0.1 现场日志（2026-11-07 19:05，COM5）

```
[voice] trigger rms=515 floor=90 thr=450
[voice] recording (rms=515, preroll=2048)
[asr] wav 64044 B -> body 85597 B (b64 45 ms)
[asr] asr: http 400 {"error":{"message":"Access denied, please make sure your
      account is in good standing. For details, see: .../error-code#over
[asr] empty result
```

`Access denied, please make sure your account is in good standing.` 在百炼对应错误码 **`Arrearage`（账号欠费）**。官方说明的原话是：「如果账户欠费，即使有资源包也无法进行调用。」

### 0.2 证据链：链路本身完全正常

| 现象 | 说明 |
|---|---|
| 拿到了 HTTP 400 + JSON body | TLS 握手、DNS、WiFi、路由全部通过 |
| `wav 64044 B -> body 85597 B (b64 45 ms)` | WAV 头、base64 容量公式、PSRAM 全部正确 |
| 不是 401，也不是 `Model not exist.` | Key 有效、域名有效、模型名有效 |
| 拒绝发生在业务层 | 服务端完整读懂了请求，只是账号状态不合格 |

**结论：这次一行代码都不用改，充值 + 等 1~2 分钟余额刷新就能恢复。**（`docs/13` 坑 6 那种 `Model not exist.` 才是真需要改代码的。）

### 0.3 顺带暴露一个必须修的日志缺陷

`cloud_asr.cpp:360`：

```cpp
Serial.printf("[asr] asr: http %d %.160s\n", code, err.c_str());
```

`%.160s` 刚好把响应里的 `"code":"Arrearage"` 那一格切掉了，只剩一句英文套话——所以只能靠查文档反推。**这条日志本身要列进本次改动**，不然后面换到腾讯云，遇到 `AuthFailure.SignatureFailure` 和 `SignatureExpire` 照样分不清。

### 0.4 决策：先止血，再迁移

| | A 充值救火 | B 迁移腾讯云 |
|---|---|---|
| 耗时 | 5 分钟 | 约半天 |
| 代码改动 | 零 | 6 改 3 增 |
| 解决什么 | 灯立刻能用 | 10~13 s 延迟、模型名频繁下架、账号单点 |
| 遗留什么 | 延迟仍在、模型名随时再变 | 三套凭据、需固件自签 TC3 |

**建议 A 和 B 并行，A 先做。**

理由：迁移过程要反复烧板、反复改签名、反复对日志，中间没有一条能用的链路，排错就退化成「同时怀疑两个变量」——`docs/13` 九个坑里有五个都是这么来的。几十块钱买一个对照组，很值。

如果已经决定彻底不再用阿里云（这个判断是合理的：10~13 s 延迟 + 一个月内模型下架两次），跳过 A 直接走 B，但要有心理准备——**从 P0 到 P4 的这几个小时里，台灯的语音是哑的**，只能按键和串口。

## 一、先说三条结论（会影响你的预期）

### 1. 腾讯云不是「一个 API Key」

| 环节 | 凭据形态 | 鉴权方式 |
|---|---|---|
| 语音识别 一句话识别 | **SecretId + SecretKey**（CAM 密钥，`AKID...` + 32 位串） | TC3-HMAC-SHA256 签名，每次请求现算 |
| 大模型（TokenHub / 混元） | **API Key**（`sk-...`） | `Authorization: Bearer`，和现在一样 |

所以串口要写**三个值**，不是两个。好在这个仓库已经有「NVS + secrets.h 双来源」的机制，扩一个字段即可，不算重构。

### 2. 腾讯云 ASR 不吃裸 PCM、也不吃「带换行的 base64」

百炼那条链路的两个坑会以另一种形式再出现一次：

- 腾讯云 `VoiceFormat=wav` 时**接受**完整 WAV（含 44 字节头），这点和百炼一致，`writeWavHeader()` 可直接复用；
- 但官方明确要求 **「编码后的数据不可带有回车换行符」**。而 `mbedtls_base64_encode()` 默认每 76 字符插一个 `\n`——`docs/13` 坑 5 里那个 `rc=-42` 的同源问题，这次不是缓冲区不够，而是**内容里有换行会被服务端拒**。必须原地压掉。

### 3. 固件现在没有系统时钟，而 TC3 签名强依赖它

这是本次改造最大的隐藏风险，比签名算法本身更麻烦。

- TC3 要求 `X-TC-Timestamp` 与腾讯云服务器相差 **≤ 5 分钟**，`Date` 必须由该时间戳按 **UTC+0** 推导；
- 全仓库 `grep configTime/sntp` **零命中**。`main.cpp:446` 那句 `time(nullptr) > 1600000000` 的条件从来没成立过——因为没人对时，`time(nullptr)` 一直是 0；
- 串口 `time <epoch>` 命令（`main.cpp:679`）只调 `timers::setEpoch()`，改的是定时器内部计数，**不动系统时钟**。

结论：**不先补 SNTP，签名必失败**，而且失败得很难看——签名过期（`AuthFailure.SignatureExpire`）和签名算错（`AuthFailure.SignatureFailure`）是两条不同错误码，会把人带偏。

## 五、核心难点一：TC3 签名怎么在 ESP32 上落地

### 5.1 算法本身是四段固定拼接

```
CanonicalRequest =
  POST\n
  /\n                       ← API 3.0 固定为 "/"，不带 query
  \n                        ← query 空串
  content-type:application/json; charset=utf-8\n
  host:asr.tencentcloudapi.com\n
  x-tc-action:sentencerecognition\n     ← 注意：这里必须小写
  \n
  content-type;host;x-tc-action\n
  sha256_hex(body)

StringToSign =
  TC3-HMAC-SHA256\n
  <X-TC-Timestamp>\n
  <yyyy-mm-dd>/asr/tc3_request\n
  sha256_hex(CanonicalRequest)

SecretDate    = HMAC("TC3" + SecretKey, date)
SecretService = HMAC(SecretDate, "asr")
SecretSigning = HMAC(SecretService, "tc3_request")
Signature     = hex(HMAC(SecretSigning, StringToSign))

Authorization: TC3-HMAC-SHA256 Credential=<SecretId>/<date>/asr/tc3_request,
               SignedHeaders=content-type;host;x-tc-action, Signature=<sig>
```

三个必踩点，写在代码注释里：

1. `date` 必须由 `X-TC-Timestamp` 按 **UTC+0** 推，不能用本地时区。东八区凌晨跑会「白天成功、夜里失败」。
2. `x-tc-action` 的**值**在 canonical headers 里是小写，但实际发送的 `X-TC-Action` 头是 `SentenceRecognition`（驼峰）。这两个不一致是设计如此，不是笔误。
3. `content-type` 签的是 `application/json; charset=utf-8`，**发送时必须一字不差**。有些 HTTP 封装会自动加/去 charset，签完再被改写就必然 `SignatureFailure`。

### 5.2 固件侧的依赖全部现成

`cloud_asr.cpp` 已经在用 `mbedtls/base64.h`，说明 mbedtls 链进来了。签名只需要再加两个头：

```cpp
#include <mbedtls/md.h>        // HMAC
#include <mbedtls/sha256.h>    // SHA256
```

不需要新库、不改 `lib_deps`、不增加分区压力。`.pio` 现在 Flash 16.0% / RAM 40.0%，加这个签名模块的增量在 3~5 KB 量级，可忽略。

### 5.3 独立成文件，先能离线自测

新增 `firmware/include/tc3_sign.h` + `firmware/src/tc3_sign.cpp`，只做纯函数，不碰 WiFi：

```cpp
namespace tc3 {
// body 已在内存里，SHA256 一趟扫完，不额外分配
String authorization(const String& secret_id, const String& secret_key,
                     const String& host, const String& service,
                     const String& action_lower, const String& version,
                     const uint8_t* body, size_t body_len,
                     uint32_t ts_utc, String* out_canonical);
}
```

`out_canonical` 是为了联调：串口打出来能直接和 Python 参考实现逐字节 diff。**这一步做扎实，后面上板就只剩网络问题。**

### 5.4 补 SNTP：这是前置条件，不是可选项

改 `wifiTick()`：WiFi 连上的那一刻起一次对时，没成功就每 10 s 重试。

```cpp
// main.cpp，WiFi 连上分支内
if (!timeSynced) {
    configTime(0, 0, "ntp.tencent.com", "cn.pool.ntp.org", "ntp.aliyun.com");
    timeSynced = time(nullptr) > 1700000000L;   // 2023-11 之后即为有效
}
```

配套两件事：

- `cloudasr::transcribe()` 里加硬闸：`if (time(nullptr) < 1700000000L) { Serial.println("[asr] clock not synced, dropped"); return ""; }`。宁可回一条明确日志，也不要发一个注定 `SignatureExpire` 的请求。
- 串口 `time <epoch>` 改成**真正设系统时钟**（`settimeofday()`），而不只是 `timers::setEpoch()`。现场没网时靠手机看一眼时间手填，比等 NTP 快。

## 六、核心难点二：三套凭据怎么存、怎么写

### 6.1 沿用现有双来源机制，只加一个字段

优先级不变：**NVS（串口命令） > 编译期常量（`secrets.h`）**。

| 用途 | NVS key | `secrets.h` 宏 | 串口 |
|---|---|---|---|
| 腾讯云 SecretId | `ak` | `LAMP_CLOUD_API_KEY` | `key <SecretId> <SecretKey> <TokenHubKey>` |
| 腾讯云 SecretKey | `sk` | `LAMP_CLOUD_SECRET_KEY` | 同上 |
| TokenHub API Key | `lk`（新增） | `LAMP_CLOUD_LLM_KEY`（新增） | 同上 |

复用 `ak`/`sk` 这两个 NVS 槽位的好处：不用清 NVS、不用改 `begin()` 的读取逻辑，只是**语义从「百度 AK/SK」变成「腾讯 SecretId/SecretKey」**。代价是仓库里如果还留着百度的旧值，切到 provider=4 后会拿着百度的 key 去签名，报 `AuthFailure.SecretIdNotFound`——排错表里写清楚就行。

`setKey()` 的签名从两参扩到三参（第三参默认 `nullptr`，百度/百炼路径不受影响）。

### 6.2 安全提醒（现在就该定，别等量产）

把 SecretKey 烧进设备，等于每台灯都揣着一把能调用你整个 ASR 服务的钥匙。现阶段自用台架可以接受，但有三条底线：

1. **用子账号密钥**，只授 `QcloudASRFullAccess`，绝不用主账号密钥；
2. 控制台开**用量告警 + 日限额**，跑飞了能兜住；
3. 真要量产，走**云函数代理**（见 §10 方案 C），设备侧只留一个可吊销的短 token。

```cpp
// 2) base64：mbedtls_base64_encode 后原地压掉 '\n'（腾讯云明确不接受换行）
size_t w = 0;
for (size_t r = 0; r < b64_len; ++r)
    if (b64[r] != '\n' && b64[r] != '\r') b64[w++] = b64[r];
b64_len = w;

// 3) 拼 JSON：注意 Data 是裸 base64，没有 data:audio/wav;base64, 前缀
//    DataLen 是「未 base64 前」的字节数 = 64044
//    UsrAudioKey 每次唯一，用 millis() 后缀即可
// 4) 签名 + POST，解析 Response.Result
```

**新增**：错误分支要按 Code 分类打印，不要只吐一句 message。

```cpp
if (!doc["Response"]["Error"].isNull()) {
    const char* code = doc["Response"]["Error"]["Code"] | "?";
    Serial.printf("[asr] tencent %s: %s\n", code,
                  doc["Response"]["Error"]["Message"] | "");
    if (strstr(code, "SignatureExpire")) timeSynced = false;  // 触发重新对时
    return String();
}
```

**改**：把 `%.160s` 的截断去掉（`cloud_asr.cpp:360`，包括百炼分支和腾讯分支）。理由见 §0.3——这次 `Arrearage` 就是这么被切掉的。改成完整打印 + 优先取错误码：

```cpp
const char* code_s = "";
```

## 八、实施顺序与验收点

分五步，每步都有明确的「过/不过」，**不过不往下走**。

| 阶段 | 做什么 | 验收标准 | 预计 |
|---|---|---|---|
| **P-1 止血**（可选） | 阿里云充值，恢复现有链路（§0.4） | 串口重新出现 `[ASR] "开灯"`，且不再 400 | 5 min |
| **P0 契约验证** | 写 `tencent_voice_check.py`，PC 上跑通两跳 | 输出「开灯」→ `on`；`--dry-run` 的签名串与 API Explorer 一致 | 30 min |
| **P1 签名库** | 写 `tc3_sign.h/.cpp`，固件里加一条串口自测 `tc3 selftest` | 固件打印的 Authorization 与 Python 版**逐字节相同**（同一 timestamp 下） | 1 h |
| **P2 ASR 接入** | `transcribeTencent()` + SNTP + 时钟闸 | 串口 `[ASR] "开灯"`，`[asr] 64044 B -> 84550 B, 320 ms` | 2 h |
| **P3 LLM 接入** | TokenHub 第二跳 | `[LLM] "开灯" -> on`，灯亮 | 30 min |
| **P4 上板联调** | 真实说话：开灯/关灯/亮一点/夜灯 | 四条命令 4/4 命中；端到端延迟记三个样本 | 1 h |
| **P5 收尾** | 文档、指纹校验、回滚演练 | `grep` 三项校验符合预期；`-e lamp_s3` 仍能编过 | 30 min |

P0 和 P1 是这次改造的价值所在：**把「签名对不对」和「网络/固件有没有问题」彻底隔离开**。`docs/13` 里九个坑有五个是「环境与配置不对」，根因都是两类问题混在一起排查。

## 九、风险清单

| 风险 | 概率 | 表现 | 对策 |
|---|---|---|---|
| 时钟不同步 | **高** | `AuthFailure.SignatureExpire` | 新增 SNTP + 时钟未同步时拒绝发请求；`time <epoch>` 手填兜底 |
| 签名串和实际发送不一致 | **高** | `AuthFailure.SignatureFailure` | `Content-Type` 写死同一份字符串常量，签名和发送共用；`--dry-run` 对照 |
| base64 带换行 | **高** | `InvalidParameterValue.ErrorInvalidVoicedata` | 原地压掉 `\n`/`\r`；`docs/13` 坑 5 同源 |
| 服务未开通 | 中 | `FailedOperation.UserNotRegistered` | 控制台先开通「语音识别」，否则 Key 再对也调不通 |
| 账号欠费 / 资源包耗尽 | **中** | `FailedOperation.ServiceIsolate` / `UserHasNoAmount` | 就是这次 400 的同类问题；充值后自动恢复，代码无解 |
| 两套 TokenHub 入口混用 | 中 | `401002 API Key 无效` | Key 与 BaseURL 必须同站点；401002 就换另一套 |
| 模型名不存在 | 中 | 一句话错误，无 HTTP 码 | 控制台查真实模型名；注释里留备选（`docs/13` 坑 6 原样复现） |
| NVS 里残留百度旧 Key | 中 | 签名报 `SecretIdNotFound` | `key` 命令覆盖写，或 `pio run -t erase` 全擦（`docs/13` 坑 9） |
| 首字延迟仍偏高 | 中 | 端到端 > 3 s | 先量再优化：热词表、`FilterPunc=2` 减响应体、必要时砍掉第二跳 |
| VAD 误触发费钱 | **高** | 噪声也发请求 | `docs/13` 遗留问题 3 一并修：`MIC_VAD_RMS` 450 → 900~1000 |
| SecretKey 下发到设备 | 低（自用）/ 高（量产） | — | 子账号最小权限 + 限额告警；量产走云函数代理 |

预期收益（需实测确认，不作承诺）：百炼实测 ASR 单跳 10~13 s，一句话识别是成熟产品线，正常应在**亚秒到 2 s** 量级，端到端体验会有明显改善。P4 必须记三个样本再下结论。

## 十、备选方案（供对比，暂不采用）

### 方案 B：ASR 走 PC 中转

固件只发 PCM 到 `127.0.0.1` 的 Python 服务，签名、密钥全在 PC 上。

- 优点：固件零改动，密钥不落板，半小时能跑通
- 缺点：**回到「必须挂一台常开电脑」**，直接违背 `docs/12` 的插电即用目标
- 结论：只适合当 P0 的临时验证手段，不做正式方案

### 方案 C：云函数 / API 网关代理

腾讯云 SCF（函数 URL）代签 TC3，设备侧只持一个可吊销的短 token。

- 优点：密钥不下发、可限流、可换厂商不动固件、能灰度
- 缺点：多一个部署物和公网入口，有冷启动延迟和额外费用
- 结论：**量产时的正确形态**，当前阶段过度设计，先记为技术债

## 十一、回滚方案

三步任选，最慢 40 s 恢复：

1. **切编译目标**：`pio run -e lamp_s3 -t upload`，回到 provider=1（百度，或按需改回 2）；
2. **恢复阿里云**：`config.h` 里 `LAMP_ENABLE_ALIYUN 1` + `pio run -e lamp_s3_bailian -t upload`（env 已注释，取消注释即可）；
3. **降级到局域网**：`-DLAMP_CLOUD_ASR=0`，走 PC 的 Vosk + Ollama 老路径。

三条路都不需要改业务代码，这是「百炼代码保留不删」的主要理由。

---

## 十二、明确不做的事

- 不动 `server/` 下的 Ollama / Vosk 链路（`LAMP_CLOUD_ASR=0` 才用，和换云厂商无关）；
- 不加 TTS（板上只有蜂鸣器，没有 I2S 功放，`docs/13` 第二节已论证过）；
- 不引入腾讯云 SDK（C++ SDK 依赖重、体积大，纯 mbedtls 手写签名约 120 行就够）；
- 不改 VAD / 录音时长逻辑——但 `MIC_VAD_RMS` 会顺手调，因为误触发直接等于烧钱。

---

## 十三、需要你先准备的三样东西

改造可以在没有 Key 的情况下写完并编译通过（`--dry-run` 和串口自检都能跑），但**联调必须有**：

1. **腾讯云账号**：实名 + 控制台开通「语音识别」服务；
2. **CAM 子账号密钥**：`SecretId`（`AKID...`）+ `SecretKey`，权限只给 `QcloudASRFullAccess`；
3. **TokenHub API Key**（`sk-...`）：开通 `deepseek-v4.1-flash`（或 `hy3`）模型，并确认控制台显示的 Base URL 是哪一套。

拿到之后按 §8 走 P0 → P4。
