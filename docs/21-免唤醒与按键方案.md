## 0. 先纠正两个前提

> **⚠️ 2026-11-08 22:1x 更正：本文 §1 的核心结论是错的。**
> 「`detect()` 每帧都跑」属实，但由此推出「所以直说也能识别」不成立。真正的门控是
> `multinet->create(mnName, 6000)` 的 6 秒窗口：过期后进入 `ESP_MN_STATE_TIMEOUT`，
> `detect()` 不再出结果，只有唤醒词分支里的 `clean()` 能重开窗口。
> 因此「先说你好小智再开灯可以、直接说开灯没反应」这个现场现象是**真实存在**的。
> 修复见 `docs/20` §5.2 与 §9。§1 保留原文，作为「用裁剪过的日志下结论」的反面样例。

你说「不要固定你好小智」和「按键使用不了」。查完代码后，这两件事的真相是：

| 你的判断 | 实际情况 | 证据 |
|---|---|---|
| 必须说「你好小智」才能开灯 | ~~不是必需的~~ → **确实需要，但原因不是唤醒词门控** | 6 秒窗口过期后无 `clean()`，见顶部更正 |
| 按键用不了（以为没实现） | **代码是完整的**，22 行实现 + 任务已创建 | `main.c:112 btnRawPressed`、`:122 buttonTask`、`:422 xTaskCreate` |

所以真正要解决的，是下面两件不同的事：

1. **唤醒词**：不影响功能，只影响日志噪音和体验观感 → §1
2. **按键**：功能存在但没反应 → 只能是硬件或极性 → §2

## 1. 唤醒词：它现在只是一个「闪灯提示」

### 1.1 现在的真实行为

```
每一帧音频 → AFE → detect() → 匹配 5 条命令 → 执行
                ↓
         如果这一帧"像"唤醒词 → 打印一行日志 + 闪一下灯
                ↓
         然后继续 detect()，和上面完全一样
```

`main.c:275-288` 的真实结构：

```c
#if GATE_BY_WAKEUP
if (res->wakeup_state == WAKENET_DETECTED) {
    ESP_LOGW(TAG, "*** wake word detected ***");
    gpio_set_level(PIN_LED, 1);      // 闪灯
    vTaskDelay(100);
    applyLed();                       // 恢复
    multinet->clean(modelData);
}
#endif

esp_mn_state_t mnState = multinet->detect(modelData, res->data);  // ← 每帧都跑，从不跳过
```

**结论（已被 §0 更正经）：** 直接说「开灯」当时并不能开灯 —— 缺的是 TIMEOUT 后的 `clean()`。唤醒词的作用是「顺手重开了一次 6 秒窗口」，所以看起来像门控。

### 1.2 三个层次的处理，按需要选

| 层 | 做法 | 改动量 | 效果 | 风险 |
|---|---|---|---|---|
| **L1 不管它** | 直接说命令，忽略日志里的 `wake word` | 0 行 | 功能已经是你要的 | 日志噪音大；每次误触发会闪灯 |
| **L2 关掉提示** | 删掉 `#if GATE_BY_WAKEUP` 整段（9 行） | 删 9 行 | 日志干净，不闪灯 | 几乎没有 |
| **L3 卸载唤醒模型** | `sdkconfig` 里 `CONFIG_SR_WN_*_NONE=y` | 改 1 项 + 重编 | 省约 1 MB PSRAM、少一段计算 | **有风险，见下** |

**L3 的风险要说清楚**：esp-sr 官方文档明确写「Speech command recognition must be used with WakeNet」。原因是 AFE 的处理链里 WakeNet 是数据通路的一环，关掉后 `res->data` 可能为空或不完整，导致 `detect()` 全部失灵。

这个风险不能靠猜，只能靠实测。**如果要走 L3，必须先在板子上验证「关掉WakeNet后 detect 还能出结果」，再决定是否保留。**

**建议：L1 或 L2。** L1 是零成本，L2 是让日志好看。L3 省的那 1 MB 对 8 MB PSRAM 的板子意义不大。

### 1.3 一个必须澄清的概念

你提到「用麦克风对话」。这里有个容易误解的地方：

**现在这套不是「对话」，是「命令词分类」。**

| | 现在做的（MultiNet） | 真正的对话（ASR + LLM） |
|---|---|---|
| 原理 | 声学特征直接分类到 5 个类别 | 先转成文字，再理解语义 |
| 能认什么 | 只有注册过的 5 句 | 任意说法 |
| 网络 | 不需要 | 需要（或本地大模型） |
| 费用 | 0 | 按次计费 |
| 延迟 | < 500 ms | 1~3 s |
| 现状 | ✅ 已跑通 | ⬜ 缺喇叭，且需 DeepSeek Key |

所以「说开灯就开灯」这件事，MultiNet 已经做到了；「跟它聊天」是另一条路，`docs/19 §6.2` 里排到了 M4/M5。

## 2. 按键：代码在，问题在硬件或极性

### 2.1 现有实现（不需要重写）

`main.c:122-175` 已经写好的行为：

| 动作 | 效果 | 代码位置 |
|---|---|---|
| 短按 | 在 0 和 70% 之间切换 | `:163` `setLevel(sBrightness > 0 ? 0 : 70, "key:toggle")` |
| 长按 1.2 秒 | 直接到最亮 100% | `:168` `setLevel(100, "key:max")` |
| 消抖 | 30 ms | `BTN_DEBOUNCE_MS` |
| 初始化 | 输入 + 上拉，20 ms 后打印空闲电平 | `:129-141` |

任务也确实被创建了：`main.c:422` `xTaskCreatePinnedToCore(buttonTask, "btn_task", 3*1024, NULL, 3, NULL, 1);`

**所以「用不了」不可能是"没写"。**

### 2.2 诊断：一个数字就能定位

开机时固件会打印这一行：

```
I (xxx) lamp_sr: btn GPIO4 idle=1 (released)
```

**这一行是唯一需要的诊断信息。** 对着看：

| 打印内容 | 含义 | 处理 |
|---|---|---|
| `idle=1 (released)` | 极性正确，按键没被按下 | 极性没问题 → 去看 §2.3 接线 |
| `idle=0 (PRESSED -- 松开手还读按下，说明极性反了)` | **极性反了** | 改 `main.c:47` `BTN_ACTIVE_LOW 1` → `0` |
| 数字在 0/1 之间乱跳 | 引脚悬空 | 模块没接好，见 §2.3 |

如果开机日志里**根本没有这一行**，说明 `buttonTask` 没跑起来（被前面的初始化卡住了），那是另一个问题。

### 2.3 接线确认（HW-483）

`config.h:42` 写的是「面包板模式：HW-483 按键接 GPIO4」。但注意同一段注释里的警告：

> 正式 PCB 的暖白通道正好在 GPIO4，直接烧会"按键踩在输出脚上"，又没反应又危险。

也就是说 **GPIO4 在正式板上是暖白 PWM 输出**。如果这块板不是面包板配置，GPIO4 可能正被当作输出脚驱动 LED——那样按键读到的永远是输出电平，按什么都没用。

**排查顺序：**

1. **量 HW-483 的三根线**：VCC → 3.3V、GND → GND、S（OUT）→ GPIO4
2. **确认没有第二处代码在驱动 GPIO4**。lamp_sr 里只有 `main.c:38 PIN_LED = GPIO5`，没有碰 GPIO4，所以这一条在 lamp_sr 里安全
3. **模块类型**：HW-483 有带锁存和不带锁存两种。带锁存的按一下翻转一次，固件如果按"按住/松开"逻辑读，会表现为"按了没反应"

### 2.4 如果要改（三种情形对应三种改法）

| 情形 | 改哪里 | 改成什么 |
|---|---|---|
| 极性反 | `main.c:47` | `BTN_ACTIVE_LOW 0` |
| 模块是锁存型 | `main.c:163` | 改成在"电平变化时"翻转，而不是"松开时" |
| 想加功能（双击、连按） | `main.c:122-175` | 加状态机，但**不建议**——短按+长按已经够用 |

## 3. 顺带要处理的问题：误触发

现在 `detect()` 一直跑，而 prob 只有 0.14~0.47，这意味着**一句话听错也可能触发动作**。日志里 `818017` 那次 `peak=83 rms=72`（很弱）就识别成了「关灯」。

### 3.1 三个可选手段

| 手段 | 做法 | 效果 | 前提 |
|---|---|---|---|
| **prob 阈值** | `if (r->prob[i] < 0.3f) continue;` | 挡住弱信号误判 | **必须先提高 prob**，否则会把 0.153 那次正确识别也挡掉 |
| **VAD 门控** | 用 `res->vad_state` 判断有无人声，无人声不跑 detect | 挡住环境噪声 | AFE 输出里有这个字段（`esp_afe_sr_iface.h:42`） |
| **按键兜底** | 语音失灵时按键永远可用 | 保证基本可用 | 按键先修好 |

### 3.2 顺序很重要

**prob 阈值不能现在加。** 你现在的真实 prob 是 0.140~0.467，如果阈值设 0.3：

- `0.153`（开灯）→ 被挡掉 ❌
- `0.140`（关灯）→ 被挡掉 ❌
- `0.467`（关灯）→ 通过 ✅

**会把两次正确识别误杀掉。** 所以顺序必须是：

1. 先把 prob 提上去（靠近麦克风 10~20 cm 重测，看能不能到 0.6+）
2. prob 稳定在 0.5 以上后，再加 0.3 的阈值做二次过滤
3. 若 prob 提不上去，说明是模型/信号问题，那就**改用 VAD 门控**而不是 prob 阈值

## 5. 一句话总结

- **「你好小智」不是必需的**，直接说「开灯」就能开灯，它只是个闪灯提示
- **按键代码是完整的**，短按开关、长按最亮，问题在 `idle=` 这一行的数字
- **误触发暂不处理**，因为 prob 太低时加阈值会误杀正确识别，得先测出 prob 上限
- 真正的「对话」是另一条路，缺喇叭，`docs/19 §6.2` 已排期
