## 3. 构建踩坑：卡住 7~9 分钟的真正原因

### 3.1 现象

默认 `.pio/build/lamp_s3_tencent` 增量编译时，编译到 IRremoteESP8266 的中途就停住：

```
Compiling .pio/build/lamp_s3_tencent/lib021/IRremoteESP8266/ir_Daikin.cpp.o
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":50,"threshold":50,...}
```

之后 CPU 时间停在 6 秒不再增长，进程挂起 7~9 分钟没有任何输出。

### 3.2 误判过程

先怀疑过三个方向，都不是：

| 猜测 | 排查 | 结论 |
|---|---|---|
| scons 版本被升级到 4.11.1 不兼容 | `scons.py --version` 正常输出 | 否 |
| PlatformIO 在下载安装包 | `.cache/tmp/pkg-installing-*` 无新增 | 否 |
| `.sconsign313.dblite` 0 字节损坏 | 删掉后重跑，仍卡在同一位置 | 否（但文件确实是坏的） |

### 3.3 真正原因

**SCons 覆盖旧 `.o` 需要先删除，本轮累计到第 50 个时触发安全确认阈值，进程开始等待一个在非交互环境里永远不会到来的确认。**

`count:50, threshold:50` 就是这个意思 —— 第 50 次删除刚好压线。

### 3.4 解法

用干净的构建目录，全程新建、没有删除操作：

```bash
# 编译（55 秒，179 个目标，零次删除拦截）
PLATFORMIO_BUILD_DIR=<空目录> python -m platformio run -e lamp_s3_tencent

# 烧录（复用同一目录，不重新编译）
PLATFORMIO_BUILD_DIR=<同一目录> python -m platformio run -e lamp_s3_tencent -t upload
```

### 3.5 两条附带结论

- `platform_packages = platformio/tool-scons@x.y.z` **管不到 tool-scons** —— 它是 PlatformIO Core 自己的依赖，不是 `platform` 的包。写进 ini 不起作用。
- 日志用 `> build.log 2>&1` 落盘比 `| tail -n` 好：管道缓冲会让人看不到中间进度，误以为在正常编译。

## 8. 附：CI「Python 语法检查」失败的修复

### 8.1 现象

合并到 `main` 后 CI 四项里只有一项红：

| 检查 | 结果 |
|---|---|
| CI / Python 语法检查 | **Failing after 6s** |
| CI / PlatformIO 全环境编译 | Successful in 3m |
| Deploy LAMP-1 website | Successful in 13s |
| CI / 仓库卫生检查 | Successful in 4s |

### 8.2 根因

`ci.yml` 的 python 任务有两步，红在第二步：

```yaml
- name: compileall
  run: python -m compileall -q server tools
- name: 设备页面与内嵌头文件是否同步
  run: python tools/embed_console.py --check
```

`embed_console.py` 用 `read_bytes()` 原样读 `web/device.html`。而 `* text=auto` 会让 git 在检出时按平台转换换行：

| 环境 | device.html | 生成的数组 |
|---|---|---|
| Windows 工作区 | CRLF，37 561 B | 含 832 处 `0x0D` |
| Linux CI | LF，36 729 B | 只有 `0x0A` |

已提交的头文件是按 CRLF 版生成的，CI 按 LF 版重算 → 逐字节比对必然不等。**本地却因为同是 CRLF 而通过**，属于最难查的一类。

验证方法（跑一次就能确认）：

```python
raw_git  = git show HEAD:web/device.html      # LF，36 729 B
raw_disk = Path('web/device.html').read_bytes()  # CRLF，37 561 B
render(raw_git)  == 已提交头文件   # False  ← CI 走这条
render(raw_disk) == 已提交头文件   # True   ← 本地走这条
```

### 8.3 修法

三处一起改，任何一处单独修都不够：

| 位置 | 改动 | 作用 |
|---|---|---|
| `read_source()` | `read_bytes().replace(b"\r\n", b"\n")` | 产物与平台无关，CRLF 源也产出 LF 数组 |
| `write_text(...)` | 加 `newline="\n"` | Windows 上不再把 `\n` 翻成 CRLF |
| `.gitattributes` | `device.html` 与 `console_html.h` 钉 `eol=lf` | 检出即一致，不依赖脚本兜底 |

重新生成后：html 36 729 B / gzip 11 588 B，比旧版少 832 B；`firmware.bin` 1 199 664 B（少 848 B）。

### 8.4 验证方式

用干净克隆模拟 CI 的检出结果，而不是只在本地跑：

```bash
git clone -q <repo> citest -b fix/ci-console-embed-eol
cd citest
python -m compileall -q server tools      # exit=0
python tools/embed_console.py --check     # console_html.h up to date, exit=0
```

克隆后确认换行：`web/device.html` 与 `console_html.h` 均为 **CRLF=0**，说明 `eol=lf` 已生效。

### 8.5 教训

**凡是「本地生成 → 提交 → CI 逐字节比对」的流程，必须先消除换行差异。** 判断方法很简单：在干净克隆里跑一遍检查，而不是只看工作区。
