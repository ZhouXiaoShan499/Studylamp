## 0. 一页纸摘要

| 问题 | 答案 |
|------|------|
| 调几个接口 | **3 个**：一句话识别、语音合成、混元 / TokenHub。前两个共用一套 TC3 签名代码。 |
| 要几个凭据 | **3 个**：SecretId、SecretKey（TC3 用）+ 一个 `sk-` 模型 Key（Bearer 用）。 |

## 1. 前提：两条固件线，只有一条能上网

这是整套方案里最容易搞错的地方。

| 固件线 | 位置 | 网络能力 | 能调云 API 吗 |
|--------|------|----------|----------------|
| `lamp_sr` | `firmware/idf/lamp_sr`（ESP-IDF 5.4.3 + esp-sr） | **无 Wi-Fi**，纯离线命令词，只打串口 | ❌ 不能 |
| 功能固件 | `firmware/src`（PlatformIO / Arduino） | Wi-Fi + `cloud_asr.cpp` + `voice_client.cpp` + `configTime` | ✅ 能 |

所以「接腾讯云」不是给现在烧在板上的固件加个接口，而是**回到 `firmware/src` 那条线**，把 provider 从百度/百炼换成腾讯。

两条线的取舍要提前认：

| | `lamp_sr` 离线 | `firmware/src` 云端 |
|---|---|---|
| 响应 | 亚秒级，不出网 | 依赖网络，1～3 s |
| 能力 | 5 条固定命令词 | 开放问答 |
| 花钱 | 0 | 按次计费 |
| 现在状态 | 已烧录、已验证 3/3 | 代码在、未接腾讯 |

**结论**：短期是二选一，不是叠加。真要「既快又能问答」，正确做法是离线命令词先兜住高频动作、云端只处理开放问题——但那是两套代码合并，属于后话，本文不展开。

## 2. 三个接口，两套鉴权

| 环节 | 端点 | Action / 版本 | 鉴权 | 返回 |
|------|------|---------------|------|------|
| 听 | `asr.tencentcloudapi.com` | `SentenceRecognition` / `2019-06-14` | TC3-HMAC-SHA256 | `Response.Result` 文本 |
| 说 | `tts.tencentcloudapi.com` | `TextToVoice` / `2019-08-23` | **同一套 TC3** | `Response.Audio`（base64） |
| 想 | `api.hunyuan.cloud.tencent.com` | `/v1/chat/completions` | `Authorization: Bearer sk-...` | OpenAI 兼容格式 |

三点判断：

1. **ASR 和 TTS 共用一套签名代码。** 都是 API 3.0，差别只有 `host`、`service`、`Action` 三个常量。所以「多接一个 TTS」不是第二套鉴权，是第二个 Action。
2. **模型侧是另一套。** 混元/TokenHub 走 OpenAI 兼容协议，`Bearer` 就够了，不需要签名、不需要对时。这也是为什么「只换模型」永远比「加语音」便宜。
3. **不存在「一把 Key 走完三跳」。** `docs/14` §1 的结论仍然成立，本文只是把「3 个凭据」这件事再确认一次。

> 版本号是硬编码在请求头里的，写错了报 `InvalidParameter`，不会自动兼容。升级接口时必须同步改常量，这点和模型名一样是易耗品。

## 3. 目标链路

```text
INMP441 ──I2S──> ESP32-S3 (firmware/src · Wi-Fi + SNTP)
                    │
                    ├─ ① HTTPS → asr.tencentcloudapi.com
                    │     SentenceRecognition  16k_zh / wav / base64
                    │     Authorization: TC3-HMAC-SHA256 …（现算）
                    │     └─→ "开灯"
                    │
                    ├─ ② HTTPS → api.hunyuan.cloud.tencent.com
                    │     /v1/chat/completions
                    │     Authorization: Bearer sk-…
                    │     └─→ "好的，已为你开灯。"（或单标签 on）
                    │
                    └─ ③ HTTPS → tts.tencentcloudapi.com
                          TextToVoice  80 字 / 16k / wav
                          Authorization: TC3-HMAC-SHA256 …（同一套代码）
                          └─→ base64 PCM → 解码 → I2S → MAX98357 → 喇叭
```

**串行还是并行**：①② 必须串行（要文本才能问模型），③ 可以和「动作执行」并行——灯先亮，声音后到。这条对体感影响很大，实施时别把三跳写成一条直线。

## 4. 设备端只补三件事

业务逻辑（录音、VAD、命令分发、灯/舵机）一行不改，新增的是「怎么把请求发出去」。

### 4.1 SNTP 对时（前置条件，不是优化项）

- TC3 要求 `X-TC-Timestamp` 与服务器相差 **≤5 分钟**；`date` 必须由时间戳按 **UTC+0** 推。
- 现状：全仓库 `configTime` / SNTP **零调用**，`time(nullptr)` 恒为 0，签名必然失败，而且报的是 `AuthFailure.SignatureExpire`——看起来像「签名算法错了」，实际是「表不准」。
- 做法：Wi-Fi 连上即对时，失败 10 s 重试；未对时**直接拒发**并打一行明确日志，不要发一个注定失败的请求。

### 4.2 TC3-HMAC-SHA256 签名

- 四段固定拼接（CanonicalRequest → StringToSign → 派生密钥 → Authorization），约 120 行。
- 依赖现成：`mbedtls/md.h`、`mbedtls/sha256.h`，不加库、不加分区。签名模块增量 3～5 KB。
- 三个必踩点（细节见 `docs/14` §5.1）：
  1. `date` 用 UTC+0，别用本地时区——东八区凌晨会「白天成功、夜里失败」；
  2. canonical headers 里 `x-tc-action` 的**值**是小写，实际发送的 `X-TC-Action` 头是驼峰，这是设计如此；
  3. `Content-Type: application/json; charset=utf-8` 签名和发送必须一字不差，中途被 HTTP 封装改写就必定 `SignatureFailure`。

### 4.3 base64 去换行

`mbedtls_base64_encode()` 默认每 76 字符插 `\n`，而腾讯云明确要求「编码后不带回车换行」。必须原地压掉再发，否则报 `InvalidParameterValue.ErrorInvalidVoicedata`——这个错误码看着像「音频坏了」，实际是「多了换行」。

**参考体积**：2 s / 16 kHz / 16 bit 单声道 = 64044 B（含 44 字节 WAV 头），base64 后 84550 B（去换行版）。

## 5. 凭据与开通清单

### 5.1 要开三样服务

| 服务 | 控制台位置 | 不开通的报错 |
|------|-----------|--------------|
| 语音识别 | 「语音识别」→ 开通 | `FailedOperation.UserNotRegistered` |
| 语音合成 | 「语音合成」→ 开通 | 同上 |
| 混元 / TokenHub | 「大模型」→ 开通 → 创建 API Key | `401002` / 模型不存在 |

**先开通，再写代码。** 这一步没做，Key 再对也调不通，而错误码不会告诉你「你没点开通」。

### 5.2 三个值怎么存

沿用现有「NVS 优先、`secrets.h` 兜底」的机制，只加一个字段：

| 用途 | NVS key | 宏 | 说明 |
|------|---------|-----|------|
| SecretId | `ak` | `LAMP_CLOUD_API_KEY` | 语义从「百度 AK」变成「腾讯 SecretId」 |
| SecretKey | `sk` | `LAMP_CLOUD_SECRET_KEY` | 同上 |
| 模型 Key | `lk`（新增） | `LAMP_CLOUD_LLM_KEY`（新增） | `sk-...`，只给模型用 |

复用 `ak`/`sk` 槽位的好处是不用清 NVS；代价是如果里面残留百度的旧值，会拿着百度凭据去签名，报 `AuthFailure.SecretIdNotFound`——排错表里要写这一条。

### 5.3 安全底线

1. 用**子账号**密钥，只授语音识别 + 语音合成的调用权限，绝不用主账号；
2. 控制台开**用量告警 + 日限额**，跑飞了能兜住；
3. SecretKey 不进仓库、不进 Issue/PR 截图；量产时改用可吊销的短期凭据——**接口不变，只换凭据形态**。

## 6. 音频参数与限额

一次写死，别再试错。

| 参数 | 值 | 备注 |
|------|-----|------|
| `EngSerViceType` | `16k_zh` | 方言用 `16k_zh_dialect` |
| `VoiceFormat` | `wav` | 含 44 字节头，现有 `writeWavHeader()` 可复用 |
| `SourceType` | `1` | 音频数据直传 |
| `Data` | 裸 base64 | **无 `data:` 前缀、无换行** |
| `DataLen` | 原始字节数 | 不是 base64 后的长度 |
| `HotwordList` | `开灯\|10,关灯\|10,夜灯\|8` | 短句场景提升最明显的一招 |
| `FilterPunc` | `2` | 砍响应体，省带宽 |
| `Region` | **不传** | 该接口不需要 |

限额：单次音频 **≤60 s**、base64 后 **≤3 MB**。按 16 kHz 单声道算，60 s 约 1.9 MB 原始、2.5 MB base64，刚好卡在边界上——录音时长别超过 45 s，留余量。

## 7. TTS 的两个接法，选简单的那个

| | **A. `TextToVoice`（推荐）** | B. 流式 WebSocket |
|---|---|---|
| 协议 | 普通 HTTPS POST | `wss://tts.cloud.tencent.com/...` |
| 鉴权 | **TC3，与 ASR 同一套** | 另一套，签名拼在 URL query 上 |
| 返回 | base64 音频，一次拿全 | 分片推送 |
| 首字延迟 | 整段合成完才有声（80 字约 0.5～1 s） | 更快，可边生成边播 |
| 设备端成本 | 多一个 Action + 一次 base64 解码 | 多一套签名 + 分片拼帧 |
| 结论 | ✅ 先做这个 | 体感优化阶段再说 |

代价要说清楚：**一次合成有文本长度上限**（基础音色约 150 汉字量级，以接口文档为准）。超过就要分段合成、分段播放，中间会有接缝。所以回答长度不是「越短越省钱」这么简单，而是**控制在一次合成内最省事**——80 字正好。

还有个现实约束：**MAX98357 和喇叭都还没到货**。这一环现在只能验「接口通、拿到音频字节、解码正确」，**听不见**。别把它排进「今天能演示」的范围。

## 8. 三跳的超时与失败降级

语音交互最怕的不是报错，是「没反应」。每一跳都要有明确的上限和退路。

| 跳 | 超时 | 失败时怎么做 |
|----|------|--------------|
| ① ASR | 8 s | 提示「没听清，再说一次」，屏幕/灯环回待机；不重试（重试要重新录音，体验更差） |
| ② LLM | 8 s | 播固定话术「网络不太好」，同时执行本地能做的动作（开灯、计时） |
| ③ TTS | 6 s | 静默降级：只做动作 + 屏幕文字，不出声；不能让用户等 |
| 整体 | 12 s 硬上限 | 到点中断，回到待机，串口打一行 `pipeline timeout at hop=N` |

重试策略分开定，别一刀切：

| 错误类型 | 处理 |
|----------|------|
| `AuthFailure.SignatureExpire` | 重新对时，**重试 1 次**（这是时钟问题，不是逻辑问题） |
| 网络超时 / DNS 失败 | 重试 1 次，仍失败则降级 |
| `InvalidParameter*` / `FailedOperation.UserNotRegistered` | **不重试**，重试也是同一个结果，直接打完整错误体 |

**优化项（不是第一步）**：回答按标点切句，第一句合成完就开始播，后面的句子边播边合成。多花几次调用，但首字延迟能压到 1 s 以内——体感提升比换模型明显。

## 9. 成本测算

按「每天 30 次对话、每次 10 s 语音、回答 80 字」估：

| 项 | 用量 | 单价（以控制台账单为准） | 每天 | 每月 |
|----|------|--------------------------|------|------|
| 一句话识别 | 5 分钟 | 0.013 元/分钟（新版大模型） | 0.07 元 | 2.0 元 |
| 语音合成 | 2400 字 | 3.00 元/万字符 | 0.72 元 | 21.6 元 |
| 混元 | — | lite 档有免费额度，超出约 0.008 元/千 token | ≈0 | ≈0 |
| **合计** | | | **≈0.79 元** | **≈24 元** |

三个结论：

1. **TTS 占 92%。** 想省钱砍回答长度，砍 ASR 没用。
2. 回答从 80 字降到 40 字，TTS 减半，月成本降到约 13 元——而且更符合桌面机器人的语气（它不该长篇大论）。
3. ASR 有两套计费口径（按分钟 / 按次千次），**别混算**，控制台看到的和文档写的可能不是同一套。

## 11. 实施顺序与验收

每步都有「过/不过」，不过不往下走。

| 阶段 | 做什么 | 验收 | 估时 |
|------|--------|------|------|
| **P0 开通与契约** | 控制台开通三服务 + 建子账号 + §10 三连测 | 三连测全部返回预期结果 | 0.5 h |
| **P1 参考实现** | 纯标准库脚本（`hmac`+`hashlib`+`urllib`）跑通 ASR → LLM 两跳 | 「开灯」→ `on`；`--dry-run` 与 API Explorer 一致 | 0.5 h |
| **P2 签名上板** | `tc3_sign.h/.cpp` + 串口自测命令 | 同一 timestamp 下，固件打印的 Authorization 与 Python 版**逐字节相同** | 1 h |
| **P3 ASR 接入** | `transcribeTencent()` + SNTP + 时钟闸 | 串口 `[ASR] "开灯"`；体积 64044 → 84550 B | 2 h |
| **P4 LLM 接入** | 第二跳 Bearer | 「开灯」→ 灯亮，端到端记 3 个样本 | 0.5 h |
| **P5 TTS 接入** | `TextToVoice` + base64 解码 | 拿到音频字节、解码正确；**听感验收等喇叭到货** | 1 h |
| **P6 收尾** | 指纹校验、回滚演练、本文补实测数据 | `grep` 指纹符合预期；`-e lamp_s3` 仍能编过 | 0.5 h |

P1、P2 是整个方案的价值所在：**把「签名对不对」和「网络/固件有没有问题」彻底隔离开**。`docs/13` 记录的九个坑里有五个，根因都是两类问题混在一起排查。

## 12. 风险与坑

| 风险 | 概率 | 表现 | 对策 |
|------|------|------|------|
| 设备无系统时钟 | **高** | `AuthFailure.SignatureExpire` | SNTP + 未对时拒发 + 串口手填兜底 |
| 签名串与实际发送不一致 | **高** | `AuthFailure.SignatureFailure` | `Content-Type` 用同一个常量，签名与发送共用；`--dry-run` 对照 |
| base64 带换行 | **高** | `InvalidParameterValue.ErrorInvalidVoicedata` | 原地压掉 `\n`/`\r` |
| 服务未开通 | 中 | `FailedOperation.UserNotRegistered` | 先点开通再写代码 |
| 账号欠费 | 中 | `FailedOperation.ServiceIsolate` | 余额告警；充值后自动恢复，代码无解 |
| 模型名被下架 | 中 | 一句话错误，无 HTTP 码 | 注释里留备选模型（`docs/13` 已栽过一次） |
| NVS 残留旧 Key | 中 | `SecretIdNotFound` | `key` 命令覆盖写，或全擦 |
| 回答超长导致 TTS 分段 | 中 | 播报有接缝、重复 | 提示词限长，80 字以内 |
| 凭据随设备流出 | 低（自用）/ 高（量产） | — | 子账号 + 限额；量产换短期凭据 |
| 延迟不达预期 | 中 | 端到端 > 3 s | 先量再优化：热词、`FilterPunc`、砍串行、③ 与动作并行 |

**延迟基准（未实测，P4 必须记样本）**：一句话识别正常应在亚秒到 2 s；混元首 token 0.5～1 s；TTS 整段合成 0.5～1 s。三跳串行合计 1.5～3 s。**实测前不许写进官网或对外材料。**

## 13. 不做清单

- 不在 `lamp_sr` 里塞网络代码——那条线的价值就是「不联网也能用」。
- 不做流式 TTS、不做打断（体感优化，等喇叭到了再说）。
