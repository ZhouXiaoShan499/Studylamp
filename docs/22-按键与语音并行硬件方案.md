## 0. 结论先说：代码已经支持并行，一个字都不用改

你的需求「按键和麦克风同时可以运行」，**在固件里已经是这样了**。这不是待实现的功能，是已实现的设计。

证据（`main.c:388-423`）：

```c
sStateMux = xSemaphoreCreateMutex();          // 共享状态互斥锁

if (micInit() != ESP_OK) { return; }

xTaskCreatePinnedToCore(srTask,     "sr_task",  8*1024, NULL, 5, NULL, 1);  // 语音
xTaskCreatePinnedToCore(buttonTask, "btn_task", 3*1024, NULL, 3, NULL, 1);  // 按键
```

| 设计点 | 实现 |
|---|---|
| 两个独立任务 | ✅ `sr_task`（优先级 5）+ `btn_task`（优先级 3），同在 core 1 |
| 互斥保护 | ✅ `sStateMux` 保护 `sBrightness` 的读-改-写，注释写明「否则连按两下可能丢一次」 |
| 统一写入口 | ✅ 只有 `setLevel(level, src)` 一个函数改亮度 |
| 来源可区分 | ✅ 日志里 `voice:on` / `key:toggle` / `key:max` 一眼看出谁触发的 |
| 引脚不冲突 | ✅ `PIN_LED=GPIO5`（输出）、`PIN_BTN=GPIO4`（输入），互不重叠 |
| 代码注释的原意 | ✅ `// 按键独立成一个任务：麦克风或模型初始化失败时，按键仍然能开关灯` |

同一份 `setLevel()` 同时服务两条输入路径：

```c
case 1: setLevel(70, "voice:on");        // 语音说「开灯」
...
setLevel(sBrightness > 0 ? 0 : 70, "key:toggle");   // 按键短按
setLevel(100, "key:max");                            // 按键长按
```

**所以「按键用不了」不是软件不支持并行，是按键这条输入路径本身没通。**

## 1. 问题定位：只需要一行日志

### 1.1 开机后固件会打印这一行

```
I (xxx) lamp_sr: btn GPIO4 idle=1 (released)
```

| 打印内容 | 含义 | 说明什么 |
|---|---|---|
| `idle=1 (released)` | 引脚空闲是高电平，极性正确 | 任务跑起来了，硬件极性问题排除 → 去 §2 |
| `idle=0 (PRESSED -- 松开手还读按下，说明极性反了)` | 极性反了 | 固件按低电平有效判断，但模块空闲输出低 → 去 §2.3 |
| `idle` 在 0/1 之间乱跳 | 引脚悬空 | 模块没接好或线松了 → 去 §2.1 |

### 1.2 如果没有这一行

说明 `buttonTask` 没被创建。有一种可能：

```c
if (micInit() != ESP_OK) {
    ESP_LOGE(TAG, "mic init failed, abort");
    return;          // ← 这里 return，下面的两个 xTaskCreate 都不会执行
}
```

**这是代码里的一个设计缺陷**：注释说"麦克风失败时按键仍能用"，但 `return` 在任务创建之前，实际会连带按键一起不启动。

不过从日志看麦克风是好的（`mic peak=` 一直在打印），所以这条基本可以排除。**除非你看到 `mic init failed`。**

## 2. 不改代码的四个办法

按「先做最省事的」排序。

### 办法 A：一根杜邦线，5 秒分清「固件问题」还是「模块问题」

`BTN_ACTIVE_LOW = 1` 意味着**低电平有效**。所以直接用一根杜邦线短接 **GPIO4 ↔ GND**，就等价于按了一次键。

```
操作：拿一根杜邦线，一头插 GPIO4，另一头碰一下 GND，然后松开
```

| 结果 | 结论 | 下一步 |
|---|---|---|
| 灯切换了（灭↔亮），日志出现 `>>> key:toggle` | **固件和引脚都正常**，问题在按键模块 | 换模块（办法 B）或改用轻触开关 |
| 灯没反应，日志也没有 `key:toggle` | 问题在引脚/固件层面 | 看 §3 |

**这是整个方案里最关键的一步。** 它把"按键没用"这个模糊问题一刀切成两半，而且零成本、零改动、不碰代码。

### 办法 B：换一个点动型轻触开关（¥1）

如果办法 A 证明固件没问题，那就是模块不对。换成最普通的三脚/两脚轻触开关：

```
一端 → GPIO4
另一端 → GND
```

**不需要任何电阻**：`main.c:129-133` 已经开了内部上拉（`GPIO_PULLUP_ENABLE`）。开关闭合 = 拉低 = 按下。

这种接法和 `BTN_ACTIVE_LOW=1` 完全吻合，**一改代码都不用**。

### 办法 C：确认 HW-483 是不是锁存型

按键模块分两种：

| 类型 | 行为 | 是否适用当前固件 |
|---|---|---|
| **点动型（momentary）** | 按住才通，松开断开 | ✅ 适用 |
| **锁存型（latching）** | 按一下锁定，再按解锁 | ❌ 不适用 |

当前固件判断的是「按住 → 松开」这个动作序列（`main.c:155-167`）。如果模块是锁存型：

- 按一下：输出翻转并**保持**
- 固件看到的是「一直是按下状态」→ 1.2 秒后触发长按最亮 → 之后再无事件
- 表现为：**按一次变最亮，再按没反应**

**判断方法**：用万用表量 S 脚对 GND 的电压，按一下松开，如果电压保持变化 → 锁存型。

锁存型的解决办法：换点动型，或按办法 B 直接换开关。

### 办法 D：检查 GPIO4 上还挂着什么

`config.h:39-46` 的注释是个重要提醒：

> 面包板模式：HW-483 按键接 GPIO4、HW-479 的 G 通道接 GPIO5。
> **正式 PCB 的暖白通道正好在 GPIO4**，直接烧会"按键踩在输出脚上"，又没反应又危险。

也就是说：**如果你这块面包板是按正式 PCB 的接法连的，GPIO4 上可能接着暖白 LED（或其他输出负载）。**

那样的话，按键读到的电平会被那个负载拉偏——永远读不到"松开"或永远读不到"按下"。

**做法**：拔掉 GPIO4 上除了按键模块之外的所有东西，只留按键。再试办法 A。

## 3. 什么情况下「不改代码」做不到

诚实说清边界。以下三种情况，纯硬件绕不过去：

| 情况 | 为什么绕不过 | 不改代码的替代 |
|---|---|---|
| 模块只能输出高电平（按下给 3.3V） | 固件按低电平有效判断 | 加一个 NPN 三极管反相，或换低电平模块 |
| 模块是锁存型且不能换 | 固件逻辑是点动式 | 换模块 |
| 引脚本身损坏 | 读不到任何变化 | 换一个 GPIO（但那必须改代码） |

**第 3 种才是真正需要改代码的**，而且只是改一行宏（`PIN_BTN`）。如果办法 A 到 D 全部无效，再考虑这条。

## 4. 执行顺序（都不改代码）

| 步 | 做什么 | 耗时 | 判断依据 |
|---|---|---|---|
| **1** | 复位板子，抓开机日志的 `btn GPIO4 idle=` | 1 分钟 | 有没有这行、值是几 |
| **2** | 杜邦线短接 GPIO4 ↔ GND，看灯是否切换 | 1 分钟 | 有 `key:toggle` = 固件好 |
| **3** | 拔掉 GPIO4 上除按键外的所有负载，重试第 2 步 | 2 分钟 | 排除负载干扰 |
| **4** | 量按键模块 S 脚电压，判断点动/锁存 | 3 分钟 | 松手后是否保持 |
| **5** | 换轻触开关直接接 GPIO4-GND | 5 分钟 | 最终验证 |

**第 2 步是分水岭。** 做完它，后面该走哪条就清楚了。

## 5. 验收标准

改完后应同时满足（这两条必须一起过，才算"并行"成立）：

| # | 验证 | 期望 |
|---|---|---|
| 1 | 说「开灯」 | `>>> voice:on level=70 LED=ON` |
| 2 | 短按按键 | `>>> key:toggle level=0 LED=OFF` |
| 3 | **紧接着**再说「开灯」 | `>>> voice:on level=70 LED=ON`（证明互不干扰） |
| 4 | 长按 1.2 秒 | `>>> key:max level=100 LED=ON` |

第 3 步是关键：连续用两种方式操作，看有没有状态错乱。`sStateMux` 就是为这个加的。
