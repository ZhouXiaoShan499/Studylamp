## 〇·五、"插电即用"和"API Key"是互斥的

这条要单独写清楚，因为它决定整个选型。

**API Key 属于云端方案，而云端方案天然做不到插电即用**，理由有三个，缺一不可：

1. **要配网**。当前 WiFi 账号写死在 `include/secrets.h`（`LAMP_WIFI_SSID "English"`），换一个房间就得重编译重烧。插电即用要求"零配置"，这条直接不成立。
2. **要联网**。没网、热点没开、路由器换了密码 → 说话完全没反应，且用户看不出是"没网"还是"坏了"。
3. **要计费**。按次调用，欠费就 400（这次现场日志就是 `Arrearage`）。插电即用的产品不能有"余额"这个隐性开关。

| 方案 | 要 Key | 要网 | 要 PC | 每次说话花钱 | 换房间能用 |
|---|---|---|---|---|---|
| 云端 ASR（百度/百炼/腾讯） | **要** | **要** | 不要 | **要** | 要重配网 |
| PC + Vosk 局域网 | 不要 | 局域网易 | **要** | 不要 | 要改 IP |
| **板上 ESP-SR / 离线模块** | **不要** | **不要** | **不要** | **不要** | **直接能用** |

**所以：要插电即用，就不要 Key；要 Key，就做不到插电即用。**

唯一的例外是"离线兜底 + 联网增强"：开关灯永远走板上离线（无 Key 也能用），AI 问答在有网有 Key 时才启用。这是小智的架构，也是长期该走的路（见 `docs/15`）。

## 二、三条路的实测数据

### 2.1 A 路：PC 端 Vosk（已验证可用）

我没有假设它能用，直接拿仓库里已有的两段录音跑了：

```
kaitest.wav  -> 开灯
guantest.wav -> 关灯
test_zh.wav  -> 你好 请 用 一句话 介绍 你自己
```

- 模型：`server/models/vosk-model-small-cn-0.22`（66 MB，**已下载好**）
- 依赖：`server/venv` 里 `vosk 0.3.45`（**已装好**）
- 特性：纯本地，不联网、不鉴权、不按次计费，延迟约 0.2~0.5 s（2 s 音频）

也就是说这条路**不是"要开发"，是"要联调"**：模型、依赖、服务端框架、固件的 WS 分支全在仓库里，只是从没端到端跑通过。

### 2.2 B 路：板上 ESP-SR MultiNet（真离线，但要 3~4 天）

- 只以 ESP-IDF 组件形式发布，`docs/12:164` 的结论是"塞进 Arduino 工程几乎无解"，需要新建独立 IDF 工程 `firmware/idf/lamp_sr/`（现有 `firmware/idf/lamp_voice` 的 `sdkconfig` 里是 `CONFIG_IDF_TARGET="esp32"`，不是 S3，只能当参考）
- 分区表要加约 2 MB 的 `model` 分区。**空间够**：当前 `default_16MB.csv` 是 app0/app1 各 6.25 MB、spiffs 3.375 MB，而固件只有 1.1 MB，从 spiffs 里切 2 MB 没有任何压力
- MultiNet6 中文命令词可自定义（拼音配置），识别率远高于自研，且带前端降噪

**代价是这 3~4 天里，灯是不能用的**（新工程里照明/定时/红外那些要重新接）。所以它不适合当"先实现"。

### 2.3 C 路：板上自研 MFCC + DTW（我试了，不达标）

我写了个纯 Python 试探脚本 `tools/kws_probe.py`，用你自己的两段录音做验证，结果如下：

| 测试 | 距离 | 期望 |
|---|---|---|
| 跨词（开灯 vs 关灯） | 3.56 | 应**远大于**同词 |
| 同词（同一段前后半） | 4.12 / 5.22 | 应**远小于**跨词 |
| 区分度 | **0.68x** | 需要 > 2x |
| 语速 ±15% 扰动 | 跨词 3.82~4.18，同词 2.49~2.69 | 仅 1.5x 余量 |
| SNR 10 dB | 跨词 1.79，同词 2.99 | 反向，失效 |

**失败原因是结构性的，不是调参能救的**：「开灯」和「关灯」共享第二个音节"灯"，只有第一个音节有区分度。模板匹配把 0.33 s 里那点差异平均掉了。

同词那一栏的测法本身偏严（把一段切成两半，等于拿"开"去比"灯"），但它足以说明一件事：**这条路的余量太薄，换个人、退半米、有风扇就会翻车**。所以我不建议在板上手搓 KWS——省下来的 3 天，会在"为什么时好时坏"上还回去。

> 这个脚本留在 `tools/kws_probe.py`，是负面结论的证据。**不要把它当成待实现的模块。**

## 三、推荐路线

**今天：A 路，1 小时出结果。之后要脱离 PC，再走 B 路。**

先做 A 的理由，不是"它简单"，而是：

1. **它是 B 的验收基线**。同一批语料、同一套"说 10 次中几次"的判定标准，先跑出一个数字（比如 9/10）。等 B 做完，直接对比，才知道这 3 天值不值。
2. **它把"识别"和"点灯"两个变量彻底分开**。`docs/13` 九个坑里五个都是这两个混在一起查的——先用一个已知能用的识别器，把下游（VAD、录音长度、cmd 下发、灯响应）全部钉死。
3. **`docs/11:151` 已经把「PC + Vosk」写成开发期 ASR**，这是既定方案，不是临时凑合。

## 四、P0 改动清单（4 处，都有明确位置）

### 4.1 `platformio.ini`：新增一个环境

```ini
[env:lamp_s3_lan]
extends = env:lamp_s3
build_flags =
    ${env:lamp_s3.build_flags}
    -DLAMP_CLOUD_ASR=0        ; 走局域网 WS，不碰任何云
```

不动 `lamp_s3`（默认 provider=1）和 `lamp_s3_bailian`，产物落在 `.pio/build/lamp_s3_lan/`，三个版本可以来回烧不用改文件。

> **已实测**：用命令行临时注入同一个宏（不改任何文件）——
> `PLATFORMIO_BUILD_FLAGS="-DLAMP_CLOUD_ASR=0" pio run -e lamp_s3` → **SUCCESS，39.7 s**。
> 说明局域网分支的代码是完整可编的，不是"写完没验证过"。新增 `[env:lamp_s3_lan]` 只是把它固化下来，避免每次都要记命令行参数。

> **注意**：`lamp_s3` 默认是 `LAMP_CLOUD_ASR=1` + `PROVIDER=1`（百度）。现在随手 `pio run -e lamp_s3 -t upload` 烧上去，说话只会得到欠费/鉴权错误——这也是现场那三条 `http 400` 的来源之一。以后默认环境建议改成"离线"，云环境单独命名。

### 4.2 `server/voice_server.py`：加 `--no-llm`

**这是目前唯一真正的阻塞点。** 看 `voice_server.py:257-262`：

```python
try:
    answer, elapsed_ms = await asyncio.to_thread(brain.ask, prompt)   # Ollama
except Exception:
    await send_json(ws, {"type": "error", ...}); return                # ← 直接返回
...
for cmd in cmds:                                                      # 永远走不到
    await send_json(ws, {"type": "cmd", **cmd})
```

`cmd` 是在 LLM **之后**才下发的。所以 Ollama 没起、或以后接 DeepSeek 但 Key 没填时，**识别得再准，灯也不会动**。

改法（约 25 行）：

```python
if args.no_llm:
    text = asr_text
    cmd = fallback_command(text)          # 已有的关键词兜底，:116
    if cmd:
        await send_json(ws, {"type": "cmd", **cmd})
    await send_json(ws, {"type": "reply", "text": f"执行 {cmd}" if cmd else "没听懂",
                         "asr": text, "elapsed_ms": 0})
    return
```

同时把"先发 cmd、再发 reply"的顺序在 `--no-llm` 下提前，这样即使以后 LLM 超时，灯该亮还是亮。

### 4.3 `include/secrets.h`：改服务器 IP（**现在这个值是错的**）

```
当前写的是  LAMP_VOICE_SERVER_HOST "192.168.42.97"
```

但现场日志里板子拿到的是 `ip=192.168.137.211`，这是 Windows 移动热点的网段（PC 侧是 `192.168.137.1`）；而此刻这台 PC 上根本没有 137 网段，只有 `WLAN 192.168.100.199` 和 `以太网 10.1.41.91`。

**所以第一步是统一网段**：要么开热点让板子连（然后 host 填 `192.168.137.1`），要么把板子和 PC 都连同一个路由（host 填 `192.168.100.199`）。填错的表现是串口一直停在 `connecting to ws://...`，反复重连，不报别的错。

### 4.4 `config.h`：VAD 阈值 450 → 900

现场日志里三条触发：

```
trigger rms=515 floor=90  thr=450   ← 误触发
trigger rms=459 floor=94  thr=450   ← 误触发
trigger rms=832 floor=109 thr=450   ← 误触发
```

真人说话是 1400~3300（同一个日志里）。三个误触发全部落在 450~850 之间，所以 900 能一刀切掉，且离真实语音还有 500 以上的余量。

```cpp
constexpr float MIC_VAD_RMS = 900.0f;   // 原来 450
```

云 ASR 时代误触发只是白花一次请求；换成离线后它更糟——每次误触发都会录 2 s 噪音去做一次识别，**可能直接点错灯**。这个必须一起改。

## 六、已知限制（必须提前接受）

1. **这不叫"板上离线"，叫"局域网离线"**。PC 得开着。要真正脱离 PC，只有 B 路。
2. **没有喇叭**，所以"对话"目前是单向的：你说 → 灯动 + 串口打印。真正的"能听会说"要等 MAX98357 + 喇叭到货（`docs/11:164` 标 ⬜ 未到）。
3. **固定录 2 s**（`MIC_RECORD_MS=2000`）。说太慢会被截断，说太快后面全是静音——Vosk 能容忍，但如果以后换成对静音敏感的识别器，要改成"静音 700 ms 结束"（`MIC_SILENCE_MS` 已经定义好了，只是没用上）。
4. **Vosk small-cn 是 42 MB 小模型**，近场清晰普通话很好，远场/方言会掉。3 米外说话需要换大模型或加降噪。
5. **PC 端一旦 STOP，板子会一直重连**，不会崩，但也不会响应——`voice status` 会显示 `ws=down`。

## 七、以后接 DeepSeek 时，改哪一行

已经预留好了，固件一行不用动：

- `voice_server.py` 的 `Brain` 类现在是 Ollama `/api/generate`（`:199`）

## 八、顺带要修的一个坑

`cloud_asr.cpp:360` 的 `Serial.printf("[asr] asr: http %d %.160s\n", ...)` 用 `%.160s` 截断响应体，正好把 `"code":"Arrearage"` 那一格切掉，导致这次欠费只能靠查文档反推。

现在改起来几乎零成本：错误分支优先打 `code` 字段，正文放到 320 B 或只打前 2 KB 的 JSON 里 `code/message` 两个键。**留着它，下次照样会误导排查方向。**
