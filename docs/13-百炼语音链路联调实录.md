## 二、为什么从百度换成阿里云

原方案是两跳：百度短语音转文字 → 国产 LLM 判断动作。用户百度账号未实名，走不通，要求统一到阿里云。

口径也变了：原计划做「百炼实时多模态交互应用（带 APP ID + WSS 会话协议）」，核对后放弃，理由三条：

1. **实时多模态的模型槽只放 omni 实时系列**（`qwen3.x-omni-flash-realtime`），DeepSeek 是纯文本模型，选不进去。
2. **多模态交互套件的「语音交互应用」**确实是 ASR→LLM→TTS 云侧编排，但 LLM 基本只支持千问系列，官方文档明确写 DeepSeek-R1 / QwQ 不支持语音交互。
3. **这块板没有「说」的能力**。`config.h` 里音频输出只有 `PIN_BUZZER = 8` 的蜂鸣器，没有 I2S 功放。实时多模态的卖点是语音进语音出，出口这半边用不上，等于用全模态的单价买了个 ASR + 分类器。

**最终选型：百炼的 OpenAI 兼容模式，两跳同步 HTTPS，一个 Key 打通。**

## 三、最终链路

```
INMP441 ──I2S──> ESP32-S3 ──HTTPS──> dashscope.aliyuncs.com
                  │                   /compatible-mode/v1/chat/completions
                  │                     ├─ 第一跳 qwen3-asr-flash   （WAV+base64 → 文字）
                  │                     └─ 第二跳 deepseek-v4.1-flash（文字 → 动作标签）
                  └──> lighting.cpp / timers / ir_engine
```

两跳共用同一个 host、同一个 path、同一个 `Bearer` Key，只有 `model` 字段不同。

### 和百度方案的关键差异

| | 百度短语音 | 百炼 qwen3-asr-flash |
|---|---|---|
| 音频格式 | **裸 PCM** 直传，`Content-Type: audio/pcm` | **完整 WAV**（44 字节头）+ base64 Data URI |
| 请求体 | 二进制流 | JSON，音频塞在 `messages[0].content[0].input_audio.data` |
| 鉴权 | 先换 token（30 天有效） | 直接 `Bearer <API Key>`，无 token 环节 |
| 体积膨胀 | 无 | base64 → **+33%**，2 s 录音 64044 B 变 85597 B |
| 内存要求 | 只需 PCM 缓冲 | WAV 缓冲 + body 缓冲，共约 149 KB |

⚠️ **百炼不吃裸 PCM**，这是移植时最容易漏的一条。

## 五、联调实录：九个坑

按踩坑顺序排列，每个坑记「现象 → 根因 → 修复」。

### 坑 1：`voice say` 自测绕过 LLM

**现象**：provider=3 编译通过，但 `voice say 把灯调暗一点` 直接走关键词匹配，日志里没有 `[LLM]` 那一行。

**根因**：`voice_client.cpp` 里有三处硬编码 `#if LAMP_CLOUD_ASR_PROVIDER == 2`——`voice say` 分支、录音后分发、动作标签处理函数。provider=3 全部落进 `#else`，退回 `handleAsrText()` 关键词匹配。

**修复**：三处 `== 2` 全改 `>= 2`。

**教训**：新增枚举值时，`==` 是比较运算符里最危险的一个。能用 `>=` 就别用 `==`。

---

### 坑 2：`websocket is down, dropped`

**现象**：

```
[voice] speech detected but WebSocket is down, dropped
```

**根因**：这句话只在 `LAMP_CLOUD_ASR == 0` 时编译进固件（旧方案：PC 跑 `voice_server.py`，灯连 WebSocket）。**板上跑的是烧录之前的老固件**，用户只执行了 `pio device monitor`，没执行 `-t upload`。

**修复**：重新烧录。这条日志此后可以当作「板上是老固件」的指纹。

---

### 坑 3：`scan: -2 AP(s) visible`

**现象**：

```
[wifi] status=1 no-ssid: 扫不到这个 SSID（热点多半在 5 GHz 或太远）
[wifi] scan: -2 AP(s) visible
```

**根因**：`-2` 不是「扫到负 2 个热点」，是 ESP-IDF 的 **`WIFI_SCAN_FAILED`** 错误码。代码把 `scanNetworks()` 放在 `WiFi.begin()` 之后、射频仍在后台连接时执行，两个操作抢同一个射频（ESP32 单工），扫描直接失败。

**修复**：扫描前先 `WiFi.disconnect(true)` 关射频，`delay(80)` 等复位，再扫。

```cpp
if (started && !scanned) {
    scanned = true;
    WiFi.disconnect(true);   // 关射频，释放给扫描
    delay(80);
    const int n = WiFi.scanNetworks();
    ...
}
```

**教训**：ESP32 的 `scanNetworks()` 返回负值一律是错误码，不能当数量用。`-1` = 忙，`-2` = 失败。

---

### 坑 4：SSID 对不上（耗时最久）

**现象**：扫描修好后，29 个 AP 全列出来了，但没有一个叫 `English`，也没有 `<== match`。

```
[wifi] scan: 29 AP(s) visible
[wifi]   -40 dBm ch11 ChinaNet-r64r
[wifi]   -51 dBm ch3  buchi2.4G
[wifi]   -68 dBm ch1  wei
[wifi]   -68 dBm ch1  wei_Wi-Fi5
...
```

**排查过程**：先后填过 `荣耀80 SE` → `rongya80` → `English`，三次都不在空口列表里。用户确认「热点名、密码、频段都没问题」。

**根因**：手机热点当时没有真正广播该 SSID（荣耀/华为热点在无设备连接时会进低功耗待机、暂停信标；或总开关实际是关的）。

**修复**：**改用 Windows「移动热点」**，把网络名和密码设成与 `secrets.h` 完全一致。Windows 热点是标准 2.4 GHz 广播，没有厂商的智能省电逻辑。

**教训**：
- 扫描列表里没有目标 SSID，就是物理层没广播，跟固件、跟代码、跟密码都无关。
- 判断「热点在不在」最快的办法：**用电脑的 WiFi 列表看一眼**，有就是 ESP32 这侧的问题，没有就是手机那侧的问题。
- 手机上看到 `wei` / `wei_Wi-Fi5` 这种成对出现、同频道同信号强度的，是同一台设备同时广播 2.4G 和 5G。ESP32 只能连不带 `_Wi-Fi5` 后缀的那个。

---

### 坑 5：`base64 failed rc=-42`

**现象**：WiFi 通了，录音也录了，卡在编码：

```
[voice] recording (rms=527, preroll=2048)
[asr] base64 failed rc=-42
[asr] empty result
```

**根因**：`-42` = **`MBEDTLS_ERR_BASE64_BUFFER_TOO_SMALL`**。

`mbedtls_base64_encode()` 默认**每 76 个字符插一个换行符 `\n`**。而原容量公式只算了纯 base64 字符数：

```cpp
const size_t b64_cap = 4 * ((wav_bytes + 2) / 3);   // 少算了换行符
```

2 s 录音 `wav_bytes = 64044` → 纯 base64 是 85392 B，加上换行符实际需要约 86500 B，差约 1100 B。

**修复**：

```cpp
const size_t b64_cap = 4 * ((wav_bytes + 2) / 3) + (wav_bytes / 57) + 16;
```

**验证**：修完后 `[asr] wav 64044 B -> body 85597 B (b64 45 ms)`，一次通过。

**教训**：mbedtls 的 base64 输出不是紧凑的，容量要按「带换行」算。`+ n/57` 是换行符数量的保守上界（76 字符一个）。

### 坑 6：`Model not exist.`（当前阻塞点）

**现象**：

```
[asr] asr: 486 B in 13125 ms
[ASR] "关灯"                          ← ASR 识别完全正确
[llm] error: Model not exist.
[LLM] "关灯" ->
[asr] empty result
```

**根因（两层）**：

1. **`deepseek-v3` 已于 2026-10-10 在百炼下架。** 不只是 v3，`deepseek-v3.1` / `v3.2` / `v3.2-exp` / `deepseek-r1` / `r1-0528` 同批下架。不是名字拼错，是模型没了。
2. 我先按官方文档猜了个 `deepseek-v4-flash`，**仍然报同样错**——因为当前账号实际可用的是 **`deepseek-v4.1-flash`**，中间那个 `.1` 不能少。

**修复**：查百炼控制台的模型列表，拿到真实模型名，改 `CLOUD_BAILIAN_LLM_MODEL`。

```cpp
// 百炼的 LLM 模型名：deepseek-v3 / deepseek-r1 等已于 2026-10-10 下架。
// 当前账号实际可用的是 deepseek-v4.1-flash（注意 .1，不是 deepseek-v4-flash）。
// 官方也推荐 qwen3.7-plus / qwen3.6-flash。报 "Model not exist." 就换备选。
constexpr const char* CLOUD_BAILIAN_LLM_MODEL = "deepseek-v4.1-flash";
```

**备选**（按「轻任务、快、便宜」排序）：

| 模型名 | 定位 |
|---|---|
| `deepseek-v4.1-flash` | **当前选用**，控制台确认可用 |
| `qwen3.6-flash` | 千问系快速版，官方推荐替代 |
| `qwen3.7-plus` | 均衡，官方推荐替代 |
| `deepseek-v4-pro` | 旗舰，本任务用不上 |

**教训**：
- 云厂商的第三方模型随时下架，**写进代码的模型名必须有「报错就换」的注释**，别当成稳定常量。
- **别信文档里的模型名，信控制台。** 官方文档写 `deepseek-v4-flash`，但账号里实际叫 `deepseek-v4.1-flash`——版本号里一个小数点，`Model not exist.` 和跑通之间就差这一格。
- 这类错误的特征是**只有一条极短的消息**（`Model not exist.`），没有 HTTP 状态码。凡看到这种"一句话错误"，先怀疑模型名/资源标识，而不是网络。

### 坑 7：`idf.py` 不能用（误判过一次）

**现象**：想用 `idf.py` 烧板，被告知「IDF 没装完」。

**根因**：我第一次用 `ls "C:/Espressif" | head -10` 查看，把排在后面的 `frameworks` 目录截掉了，误以为 IDF 未安装。**实际 `D:\Espressif\frameworks\esp-idf-v5.4.3` 完整存在，`idf.py --version` 输出 `ESP-IDF v5.4.3-dirty`。**

**真正的原因**：`firmware/` 是 PlatformIO 工程，**没有 `CMakeLists.txt`，没有 `main/`，没有 `sdkconfig`**，入口是 `setup()/loop()` 而非 `app_main()`。`idf.py build` 在 `firmware/` 直接回一行就退出：

```
CMakeLists.txt not found in project directory D:\study lamp\lamp\lamp\firmware
```

`idf.py` 不是烧录器，是 CMake 工程的驱动。`idf.py flash` 需要读 `build/flasher_args.json` 才知道「烧什么、烧到哪个地址」。`firmware/idf/lamp_voice/build/` 里有这个文件，`.pio/build/lamp_s3/` 里没有。

**另外两个环境坑**（真要切 IDF 会踩）：
1. `python_env` 只有 `idf5.4_py3.11_env`，PATH 上第一个 `python3` 是 3.13，`export.bat` 会去找 `idf5.4_py3.13_env` 并报 not found。**必须用 `D:\Espressif\idf_cmd_init.bat` 启动**。
2. `export.sh` 在 Git Bash 里被 IDF 明确拒绝（`MSys/Mingw is no longer supported`），只能用 `cmd.exe` 或 PowerShell。

**顺带纠正一处风险**：`firmware/idf/lamp_voice` 和 `pdm_probe` 的 `CMakeCache.txt` 里 `IDF_TARGET:STRING=esp32`，构建出的是 **esp32 镜像**，烧到 S3 上不启动。

### 坑 8：改了 `platformio.ini` 导致旧产物被清

**现象**：新增 `[env:lamp_s3_bailian]` 后，`.pio/build/lamp_s3/` 整个消失。

**根因**：PIO 用 `project.checksum` 判断配置变更，`platformio.ini` 一动就清空整个 `.pio/build/`。

**影响**：只发生一次，重编约 38 s。不是 bug。

**教训**：改 ini 之前先确认当前 `firmware.bin` 是哪一版，否则会像我这次一样——想抓 esptool 参数，顺手用默认配置（provider=1）重编，把磁盘上的 provider=3 固件覆盖成了 provider=1，还打出了 `SUCCESS`。

**防呆办法**：烧录前必做一次校验，返回 1 才是百炼版：

```bash
grep -ac qwen3-asr-flash .pio/build/lamp_s3_bailian/firmware.elf
```

### 坑 9：烧录日志擦除范围不包含 NVS

**现象**：担心烧录会清掉之前串口写入的 Key。

**事实**：擦除范围是 `0x00000–0x03fff`、`0x08000–0x08fff`、`0x0e000–0x0ffff`、`0x10000–0x10ffff`，**没有碰 `0x9000–0xdfff`（NVS 分区）**。

所以「之前用 `key` 命令写过的旧 Key」会一直存活，且优先级高于 `secrets.h`。表现是：看不到 `key 来自 secrets.h` 那句，但 `asr` 显示 `key=set`。

**修复**：直接 `key sk-新值` 覆盖，或 `pio run -t erase` 全擦。

## 六、串口命令手册

### 打开串口（cmd.exe）

```cmd
set PATH=%USERPROFILE%\.platformio\penv\Scripts;%PATH%
cd /d "D:\study lamp\lamp\lamp\firmware"
pio device list
pio device monitor -p COM5 -b 115200
```

- 第一行每个新开的 cmd 窗口都要跑一次（`pio` 不在系统 PATH）
- 退出：`Ctrl+C`；菜单：`Ctrl+T`
- **烧录前必须先退出监视器**，串口被占用会烧录失败

### 设备命令

| 命令 | 作用 |
|---|---|
| `asr` | 云端 ASR 状态（provider / key / wifi） |
| `key sk-xxx` | 写入 Key 到 NVS（优先级最高） |
| `voice status` | 语音子系统状态 |
| `voice listen` | 完整链路，8 s 内说话 |
| `voice say <文本>` | 只测第二跳（文字→LLM），不录音 |
| `mic test 10` | 麦克风电平自检，正常说话 rms 峰值 3000+ |
| `mic on` / `mic off` | 开关常开监听 |
| `status` | 全局状态 |
| `light 0-100` / `cct 2700-6500` | 亮度 / 色温 |
| `mode study\|office\|rest\|night` | 场景预设 |
| `help` | 全部命令 |

## 七、排错对照表

| 串口输出 | 含义 | 处理 |
|---|---|---|
| `key=missing` | NVS 与 `secrets.h` 都没值 | 检查 `secrets.h` 引号配对 |
| `wifi=down` | 未连网 | 见下方 WiFi 专项 |
| `scan: -2 AP(s)` | 扫描失败（非数量） | 检查扫描前是否 `disconnect(true)` |
| 扫描列表无目标 SSID | 热点没广播 | 换 Windows 移动热点 |
| 列表有 `xxx_Wi-Fi5` | 5 GHz 信号 | 连不带后缀的那个 |
| `status=4 auth-failed` | 能看到但密码错 | 核对密码 / 加密方式改 WPA2 |
| `status=1 no-ssid` | 扫到了却报不存在 | 基本是 5 GHz 信道 |
| `base64 failed rc=-42` | 输出缓冲不够 | 容量公式加换行符余量 |
| `oom: wav` / `oom: body` | 内存不足 | 开 PSRAM（见遗留问题 1） |
| `asr: http 401` | Key 无效 | 换 Key |
| `asr: http 404` | 域名不对 | 换带 WorkspaceId 的新域名 |
| `[llm] error: Model not exist.` | 模型名不存在（注意版本号小数点，如 `v4.1` 不是 `v4`） | 按控制台实际名改（见坑 6） |
| `[LLM] "..." -> none` | 模型没识别出动作 | 换更强的模型 |
| `[ASR] "嗯"` 之类的误识别 | VAD 阈值太低 | 调 `MIC_VAD_RMS` |

## 八、遗留问题与待办

### 1. PSRAM 没开（潜在风险，尚未爆发）

PIO 把板子识别成 **"ESP32-S3-DevKitC-1-N8 (8 MB QD, No PSRAM)"**，而 esptool 报告的是 **`Embedded PSRAM 8MB (AP_3v3)`**。

`platformio.ini` 里没有设 `board_build.arduino.memory_type`，所以 Arduino 内核按「无 PSRAM」编译，`ps_malloc()` 返回空，149 KB 缓冲（wav 64044 + body 85597）只能退到内部 RAM 的 `malloc`。

目前 `heap=227016` 够用，还没报 `oom`。但**如果同时开 WiFi + TLS + 双缓冲，余量会紧**。

修法（一行）：

```ini
board_build.arduino.memory_type = qio_opi
```

N16R8 是八线 PSRAM，`qio_opi` 是对应的组合。改完重编重烧约 40 s。**没有擅自改**，因为万一 PSRAM 实际是 quad 模式会导致不启动。

### 2. ASR 延迟 10~13 秒（体验问题）

实测三次：

```
[asr] asr: 486 B in 13125 ms
[asr] asr: 491 B in 10514 ms
[asr] asr: 486 B in 11529 ms
```

对「开个灯」这种一次性命令，10 秒不可接受。可能原因：

- 2 s 音频 base64 后 86 KB，上行本身慢（WiFi rssi −27，应该不是瓶颈）
- `stream: false` 一次性返回，模型侧冷启动
- 首次调用预热（但三次都慢，不像）
- 百炼对 `qwen3-asr-flash` 的限流或排队

**待验证**：先确认 LLM 通了、跑通完整链路，再用 `tools/bailian_voice_check.py` 在 PC 上测纯网络延迟，对比是「网络慢」还是「模型慢」。

### 3. VAD 误触发严重

```
[voice] trigger rms=498 floor=165 thr=494     ← 噪声触发
[voice] trigger rms=520 floor=132 thr=450
[voice] trigger rms=3293 floor=191 thr=572    ← 真正说话
```

`MIC_VAD_RMS = 450` 太低。环境噪声底约 130~200，噪声峰值能到 500~800，真人说话在 1400~3300。

**建议**：把 `MIC_VAD_RMS` 提到 900~1000，或改成相对阈值（`floor × 3 + 200`）。目前每 32 ms 就可能触发一次，既费流量又费钱。

### 4. LLM 模型名（已定名，待上板验证）

模型名已从控制台确认是 **`deepseek-v4.1-flash`**，`config.h` 已改，**尚未上板验证**。若仍报 `Model not exist.`，按坑 6 的备选表换 `qwen3.6-flash` / `qwen3.7-plus`。

### 5. 域名迁移风险

新控制台把 `dashscope.aliyuncs.com` 换成了 `{WorkspaceId}.cn-beijing.maas.aliyuncs.com`。当前 ASR 用老域名成功，说明账号还兼容；一旦返回 404/403，改 `CLOUD_BAILIAN_HOST` 即可，Key 不变。

### 6. 待提交

工作区改动（6 改 1 增，`+358 / -30`）尚未提交。分支 `feat/cloud-asr` 已推送到远端，这四个提交悬在分支上未合 main。

## 九、九个坑的共性总结

回头看，九个坑分成三类，比例很有代表性：

| 类别 | 坑号 | 数量 |
|---|---|---|
| **云侧契约变化**（模型下架） | 6 | 1 |
| **固件状态 / 时序 bug**（枚举比较、射频抢占、缓冲区算小） | 1、3、5 | 3 |
| **环境与配置不对**（老固件、SSID、IDF 误判、ini 清缓存、NVS 残留） | 2、4、7、8、9 | 5 |

**真正写代码写错的地方只有 3 个（枚举比较、射频时序、缓冲区容量），其余全是「环境/契约对不上」。**

对应的三条经验：

1. **烧录后先看开机横幅和新日志指纹**，确认板上跑的是刚编的那版。`websocket is down` 这个坑就是这么浪费掉的。
2. **云侧的任何字符串常量（模型名、域名、路径）都当易耗品**，注释里永远留一句「报错就换 X」。
3. **诊断日志值得写**。WiFi 那一段前后改了三轮（状态码→扫描→连接成功），每一轮都把「猜」变成了「看」。没有 `scan: N AP(s)` 这行，SSID 那个坑根本不可能定位。
