# 07 语音产品化方案（从"连电脑"到"插电即用"）

> 目标：把 LAMP-1 从一个"必须连电脑才能说话"的演示样机，改造成
> **插上电源、连上家里 WiFi，就能听懂指令并开灯的真实产品**。
> 本文是方案决策文档，不含实现代码。实现见 `docs/08-语音产品化实施手册.md`（待写）。

---

## 一、一句话结论

**采用「云端大模型」作为 v1，把 `qwen` 放到阿里云百炼；v2 再叠加「本地命令词」层把高频指令压到 0.3 秒并实现断网可用。**

- 纯电脑方案（现状）：**不可交付**，用户家里不该有一台常开的 PC
- 纯端侧方案：**物理不可行**，qwen 装不进 8 MB PSRAM
- 纯云端方案：**可交付但体验有短板**（开灯要等 1.5~2.5 秒），作为 v1 快速验证
- **混合方案（本地命令 + 云端理解）**：最终形态

---

## 二、现状盘点

项目里现在有 **三套互不兼容** 的语音实现，先认清再动手：

| # | 位置 | 传输 | ASR | 大模型 | 问题 |
|---|------|------|-----|--------|------|
| 1 | `firmware/src/voice_client.cpp`（Arduino） | WebSocket → PC:8765 | PC 上 Vosk | PC 上 Ollama | **固定录满 2 秒**再发，白送延迟；依赖电脑 |
| 2 | `firmware/idf/lamp_voice/main/lamp_voice.c`（ESP-IDF） | TCP → PC:8766 | PC 上 Vosk | PC 上 Ollama | 代码质量最好（真 VAD），但仍依赖电脑 |
| 3 | `server/lamp_server.py` | TCP 8766 + HTTP 8080 | Vosk | Ollama | 只服务方案 2 |

**关键观察**：方案 2 的 VAD 逻辑比方案 1 好得多——

```
lamp_voice.c:  VAD_START_DB(-45) / VAD_END_DB(-50)
               连续 800 ms 静音收尾，起手留 100 ms preroll，上限 8 秒
voice_client.cpp: 触发后固定录满 MIC_RECORD_MS = 2000 毫秒再一次性发送
```

固定 2 秒意味着：你说"开灯"（0.6 秒），设备还要**再空录 1.4 秒**才发出去。
**这条必须改掉**，否则后面所有延迟优化都是白做。

## 三、目标与验收标准

先写死验收标准，避免"感觉通了"。

| 指标 | v1 目标 | v2 目标 | 测法 |
|------|---------|---------|------|
| 上电到可对话 | ≤ 15 s（含 WiFi 连接） | ≤ 8 s | 秒表 |
| 说"开灯"到灯亮 | ≤ 2.5 s | **≤ 0.5 s** | 录像逐帧 |
| 断网时开灯 | ✗ 不可用 | **✓ 可用** | 拔路由器 |
| 首次配网 | 手机 3 步内完成 | 同左 | 让没看过文档的人试 |
| 误触发（电视 2 小时） | ≤ 0 次（按键门控） | ≤ 1 次/小时 | 播放电视剧实测 |
| 每台年成本 | ≤ 6 元 | ≤ 6 元 | 账单核算 |
| 无需电脑 | ✓ | ✓ | 拔掉 PC |

## 四、方案选型

| 方案 | 大模型位置 | 上电即用 | 开灯延迟 | 断网可用 | 年成本/台 | 结论 |
|------|-----------|---------|---------|---------|----------|------|
| A 电脑 + Ollama（现状） | 用户 PC | ✗ | 0.6~1 s | ✓ | 0 | **淘汰** |
| B A + 开机自启 | 用户 PC | ✗ | 0.6~1 s | ✓ | 0 | **淘汰**（仍是 PC） |
| C 纯云端百炼 | 阿里云 | ✓ | 1.5~2.5 s | ✗ | ~4.4 元 | **v1 采用** |
| D 本地命令词 + 云端 | 端侧 + 云 | ✓ | **0.3~0.5 s** | ✓ | ~4.4 元 | **v2 目标** |
| E qwen 跑在 ESP32 | 端侧 | — | — | — | — | **不可行** |
| F 树莓派/迷你主机 | 家里多一台盒子 | ✓ | 0.5~1 s | ✓ | 硬件 300~800 元 | **不做**（用户家里多一台设备，产品逻辑不成立） |

**为什么 A/B 必须淘汰**：不是技术问题，是产品逻辑问题。让用户「常开电脑 + 装 Ollama + 保证同一网段 + IP 不能变」，这是开发板，不是台灯。

**为什么 C 只能做 v1**：成本没问题，问题是「说开灯等 2 秒」用户会认为灯坏了。台灯 95% 的交互是开关灯，这类指令不需要大模型。

## 五、推荐架构

```
            ┌──────────────────────── 设备端 ESP32-S3（插电即用）────────────────────────┐
            │                                                                          │
 用户说话 → │  INMP441 ──▶ VAD ──▶ ┌─ 命中本地命令词 ──▶ 灯光/红外执行   (0.3 s)        │
            │                      │                                                   │
            │                      └─ 未命中 ──┐                                        │
            └───────────────────────────────────┼────────────────────────────────────────┘
                                                │ WiFi / HTTPS
                                                ▼
            ┌──────────────────────── 云端（厂商维护，用户无感）───────────────────────┐
            │   API 代理（验签 / 限流 / 计量）──▶ qwen-audio-asr ──▶ qwen-flash        │
            │                                          │                               │
            │                                          └──▶ 返回 {text, cmd}           │
            └──────────────────────────────────────────────────────────────────────────┘
```

### 必须理解的一个概念

> **「不插电脑」≠「没有服务器」。**

产品化的正确形态是：**用户家里只有灯和 WiFi，服务器在厂商这边**（一台云服务器代理全部设备的 API 调用，每月几十元，摊到每台几乎为零）。用户完全无感。

这与「每台灯配一台用户的 PC」是两回事。前者是产品，后者是开发板。

## 六、关键设计决策

### 6.1 v1 用「按键触发」，不用唤醒词

这是本文最重要的一个取舍。

v1 走纯云端，如果没有门控，**电视里说一句"开灯"就会触发一次 API 调用**——既误开灯，又持续烧钱（每句话都计费）。

三个候选：

| 门控方式 | 误触发 | 成本 | 体验 | 结论 |
|---------|--------|------|------|------|
| 常开 VAD 直接触发 | 高 | 持续烧钱 | 最自然 | ✗ |
| **按键触发（按住/按一下说话）** | **0** | **0** | 可接受 | **v1 采用** |
| 唤醒词（ESP-SR WakeNet） | 低 | 0 | 最好 | v2 采用 |

v1 用按键门控：用户按一下灯上的键 → 哔一声 → 说"开灯" → 执行。零误触发、零浪费、实现成本一天。

v2 再把唤醒词加上，按键保留作为兜底。

### 6.2 配网：SoftAP + 网页，不要写死 secrets.h

现在 WiFi 写死在 `secrets.h` 里，**用户买回家没有任何办法填自己的密码**。这是产品化第一道坎，比接大模型重要。

流程：

```
首次上电（NVS 无 WiFi 配置）
   ↓
开热点，SSID = "LAMP-A1B2"（MAC 后 4 位）
   ↓
手机连上 → 自动弹出配置页（captive portal）
   ↓
填 WiFi 名称 + 密码 → 提交
   ↓
设备存 NVS → 重启 → 入网成功，热点关闭
```

实现选型：

| 框架 | 方案 | 工作量 |
|------|------|--------|
| Arduino | `tzapu/WiFiManager` 库 | 半天，成熟稳定 |
| ESP-IDF | 官方 `wifi_provisioning` 组件（protocomm） | 2~3 天，支持 SoftAP/BLE |

> 配网页面要做 **WiFi 扫描列表**，让用户点选而不是手打密码——手打密码的错误率是产品退货主因之一。

### 6.3 设备鉴权：API Key 绝不下发到设备

如果把百炼 key 编译进固件，任何人拆机 dump flash 就能盗刷账号。

正确做法：**每台设备一个独立密钥，key 只存在服务器上**。

```
产线烧录（每台唯一）：
  device_id     = "LAMP-0001" ~ "LAMP-NNNN"
  device_secret = 32 字节随机数

设备请求：
  POST /v1/voice
  X-Device-Id:  LAMP-0001
  X-Timestamp:  1730000000
  X-Nonce:      随机数
  X-Sign:       HMAC-SHA256(device_secret, device_id + timestamp + nonce + sha256(body))

服务端：
  1. 查 device_id 对应的 secret
  2. 验签
  3. 时间戳 ±300 s（防重放）
  4. nonce 5 分钟内不重复
  5. 通过 → 用自己的百炼 key 转发
```

**为什么这样安全**：dump 出 flash 也只能拿到**单台**设备的密钥，厂商可以远程封禁这一台，不影响其他设备。这比泄露全局 API key 好得多。

### 6.4 延迟预算（改掉固定 2 秒是关键）

| 环节 | v1 纯云端 | v2 混合（本地命中） |
|------|----------|-------------------|
| 语音结束检测（VAD 静音） | 500 ms | 300 ms |
| 音频上传（64 KB @ WiFi） | 300~500 ms | — |
| ASR（qwen-audio-asr） | 300~500 ms | — |
| LLM（qwen-flash，限 80 字） | 400~800 ms | — |
| 下行 + 执行 | 50 ms | 50 ms |
| **合计（用户感知）** | **1.5~2.5 s** | **0.3~0.5 s** |

**优化清单（按收益排序）**：

1. **把固定 2 秒录音改成 VAD 收尾**（`lamp_voice.c` 已有此逻辑）→ 省 1~1.5 s
2. VAD 静音阈值从 800 ms 降到 **400~500 ms**（命令句短，用户不会长停顿）→ 省 0.3 s
3. 音频用 **Opus 编码**（16 kHz 单声道，64 KB → 约 6 KB）→ 上传省 0.3 s，但增加 CPU 与依赖
4. qwen 加 **system prompt 限制输出 ≤ 60 字** + `max_tokens=120` → 省 0.2 s
5. 云端 **keep-alive 连接池**，省 TLS 握手（每次省 ~0.3 s）

> v1 只做 1、2、4、5，第 3 项留到 v2 评估（Opus 编码在 ESP32-S3 上约需 30~60 ms，收益不明显）。

### 6.5 断网降级：灯不能因为断网就变砖

```
WiFi 未连上 / 云端不可达
   ↓
本地功能全部保留：
  ✓ 按键开关灯（已有）
  ✓ 红外遥控学习与发送（已有）
  ✓ 定时任务（已有，靠 millis/SNTP）
  ✗ 语音对话（不可用，串口/OLED 提示"离线"）
   ↓
每 10 秒后台重试，连上后自动恢复语音，不重启
```

`main.cpp` 的 `wifiTick()` 已经是非阻塞重连，这点做得对，**不要改成阻塞式 `WiFi.begin()` 等待**。

### 6.6 误唤醒控制（v2 才需要）

| 措施 | 说明 |
|------|------|
| 唤醒词必须两字以上、发音差异大 | "小灯小灯"优于"小灯" |
| 置信度阈值 0.65 起步 | 低于阈值让灯头轻摆表示"没听清"，不执行 |
| 同一命令 1.5 秒内去重 | 防重复触发 |
| 夜间（22:00–07:00）不响应语音开灯 | 与 `motion::setNightMode` 联动，避免半夜被电视叫醒 |
| 每日语音调用次数硬上限 | 防刷、防失控（默认 200 次/天） |

## 七、设备 ↔ 云协议（v1）

### 7.1 请求

```
POST https://api.example.com/v1/voice
Content-Type: application/octet-stream

Header:
  X-Device-Id / X-Timestamp / X-Nonce / X-Sign
  X-Audio-Format: pcm16/16000/1

Body: 裸 PCM（16 kHz 单声道 16 bit 小端），单次 ≤ 8 秒（256 KB）
```

用裸 PCM 而不是 base64，省 33% 流量和一次编解码。

### 7.2 响应

```json
{
  "asr": "把灯调到一半亮度",
  "text": "好的，调到一半。",
  "cmd": { "brightness": 50 },
  "elapsed_ms": 1380
}
```

`cmd` 直接复用现有 `applyCommand()` 的字段（`light` / `brightness` / `cct` / `preset`），
**固件侧的指令解析完全不用改**。

### 7.3 错误码

| 码 | 含义 | 设备行为 |
|----|------|---------|
| 401 | 签名失败 | 串口报错，不重试（密钥错误） |
| 429 | 超限 | 退避 60 s 后重试 |
| 503 | 云端不可用 | 进入离线模式，30 s 后重试 |
| 超时 5 s | 网络差 | 放弃本轮，提示"网络不好" |

## 八、成本模型（按百炼现价）

| 项目 | 单价 | 单次用量 | 单次成本 |
|------|------|---------|---------|
| ASR（qwen-audio-asr-flash-streaming） | 0.00033 元/秒 | 3 秒 | 0.001 元 |
| qwen-flash 输入 | 0.15 元/百万 token | ~500 token | 0.000075 元 |
| qwen-flash 输出 | 1.5 元/百万 token | ~80 token | 0.00012 元 |
| **合计** | | | **≈ 0.0012 元/次** |

| 场景 | 计算 | 结果 |
|------|------|------|
| 单用户 | 10 次/天 × 365 × 0.0012 | **4.4 元/年** |
| 1000 台设备 | 4.4 × 1000 | **4400 元/年** |

> **前提：不做语音播报。** 台灯只有蜂鸣器、没有喇叭，本来就不播报，
> 正好省掉最贵的一环（TTS 约 0.008 元/次，占成本 85%）。
> 若 v3 加喇叭做播报，成本会翻近 10 倍，需要重新核算。

## 十、分阶段路线

### v1：能交付的样机（预计 3~4 天）

| 步骤 | 内容 | 验收 |
|------|------|------|
| 1 | 改 VAD 收尾，删掉固定 2 秒录音 | 说 1 秒的话 1 秒就发出去 |
| 2 | 写 `cloud_client` + `cloud_api.py`，先不做鉴权 | 串口说"开灯"灯会亮 |
| 3 | 加 SoftAP 配网 | 手机能配网，配完自动入网 |
| 4 | 加按键触发录音 | 电视播放 2 小时，零误触发 |
| 5 | 加 HMAC 鉴权 | 改错 secret 请求被拒 |

**v1 结束标志：拔掉电脑，台灯插电 → 手机配网 → 说"开灯" → 灯亮。**

### v2：把高频指令压到 0.3 秒（预计 5~7 天）

| 步骤 | 内容 | 依赖 |
|------|------|------|
| 1 | 引入 ESP-SR（WakeNet 唤醒 + MultiNet 命令词） | 需评估框架迁移（见 11.1） |
| 2 | 20 条命令词映射到本地动作 | 命令表见 `docs/03` §9.2 |
| 3 | 本地命中直接执行，未命中才上云 | v1 完成 |
| 4 | 误唤醒调优（真实电视节目 2 小时） | 步骤 1~3 |

### v3：可小批量（持续）

- 老化测试、功耗测量（常开唤醒词会增加 50~80 mA）
- 成本优化：qwen-flash → 更小模型；ASR 改用 Paraformer（0.00024 元/秒，更便宜）
- 配网体验打磨（失败重试、密码错误提示）

## 十一、风险与对策

| # | 风险 | 影响 | 对策 |
|---|------|------|------|
| 11.1 | **ESP-SR 在 Arduino 框架下不可用** | v2 无法落地 | 官方只提供 ESP-IDF 组件。两条路：① 整体迁 ESP-IDF（工作量大，但 `firmware/idf/` 已有先例，`docs/03` §10.1 本来就是按 IDF 风格写的）；② v2 先用第三方 KWS（如 EdgeImpulse）验证效果再决定。**这条要在 v2 启动前评估清楚，不要闷头做** |

| 11.6 | 麦克风远场识别差 | "听不清" | INMP441 是近场麦，建议产品说明写"1 米内说话"；v3 可评估加数字麦阵列 |
| 11.7 | 隐私质疑 | 用户不接受上云 | 明确告知；提供"纯本地模式"开关（关掉语音，只用按键/红外） |

## 十三、本方案明确不做的事

守住边界，避免范围蔓延：

- ✗ 不做语音播报（无喇叭，也不为此加喇叭）
- ✗ 不做多轮对话上下文（台灯场景用不上，且会推高 token 成本）
- ✗ 不做手机 App（配网用网页足够；`docs/03` §1.2 已明确不做 App）
- ✗ 不做离线大模型（端侧跑不动）
- ✗ 不改硬件（不加喇叭、不换麦克风、不换主控）
- ✗ 不做唤醒词（v1 阶段）
